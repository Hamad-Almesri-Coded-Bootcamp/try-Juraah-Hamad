# Jur'ah (جرعة) — Decisions and change requests

**How this file works.** Every proposal to change, reinterpret or fill a gap in a binding document is logged here in the protocol's shape: what the document says · why it is a problem · what is proposed · what it costs · what breaks if we don't. The build continues **as written** until the owner answers, except where two binding documents contradict each other or a document cannot be built as written; in those cases the default taken is stated and marked. Answers are recorded under each item; a resolved item also names the project document that must be updated to match.

**Status legend:** `OPEN` awaiting the owner · `DEFAULT` the build proceeds on the stated default until answered · `BLOCKS` must be answered before the named work package starts · `RESOLVED`.

**Numbering.** CR numbers were assigned as findings were logged during the read; CR-013, CR-015, CR-023 and CR-024 were folded into CR-012, D-001, D-002 and D-004 respectively and their numbers retired, so the sequence has gaps.

### CR-002 · Required contract fields that the seed's flagged and returned prescriptions do not have — `RESOLVED`
- **Owner's answer (Gate 0).** Approved with a tightening: the five fields are optional **only** while `needsReview: true` or `fieldReviewStatus` is `pending` or `returned`. Two stated invariants, guard-scripted (`scripts/guards/seed-invariants.ts`): an `active` prescription with `needsReview: false` carries all five; the dose generator returns an empty array unless `startDate` is present and `doseTimes.length === frequencyPerDay`. "Optional" never means an active prescription may have no schedule. **Doc to update:** Data Contracts → `Prescription`.
- **Document says.** Data Contracts: `Prescription.startDate` REQUIRED, `doseTimes` REQUIRED with `length === frequencyPerDay`, `frequencyPerDay: number`, `drug.strengthMg: number`, `drug.brandName: string`. `Seed Dataset.md`: `rx-006` (handwritten, `needsReview: true`) has no strength, no frequency, no times, no start date; `rx-007` (returned) has times but no start date; `rx-005`, `rx-007`, `rx-009` have no brand name.
- **Why it is a problem.** WP1 must transcribe the contracts exactly *and* the seed exactly. Both cannot be true. Filling the gaps with placeholder values invents seed data; leaving them out fails the type.
- **Proposal.** Amend the contract: `startDate?`, `doseTimes?`, `frequencyPerDay?`, `drug.strengthMg?` and `drug.brandName?` become optional, each with the comment "absent only while `needsReview` is true and `fieldReviewStatus` is not `confirmed`" (brand name may also be absent for a generic-only dispensing). The schedule engine already skips such records, so nothing downstream changes. `PrescriptionCard` already treats `brandName` and `strengthMg` as optional.
- **Cost.** Five `?` marks and a comment in `types/contracts.ts` and in the spec's Data Contracts; a `DetailRow` renders its empty mark where a value is absent (it already does).
- **If we don't.** WP1 cannot start; or the seed grows invented strengths and dates for a prescription whose whole point is that they could not be read.
- **Default until answered.** WP1 transcribes the contract with the five fields optional and marks the deviation with a `// CR-002` comment.
- **Doc to update on approval.** `Acceptance Criteria and Test Plan.md` → Data Contracts → `Prescription`; `Seed Dataset.md` unchanged.
- **Spec updated (v7.4):** `Prescription` fields and the two invariants written into the Data Contracts. `Seed Dataset.md` unchanged.
- **Interpretation recorded at Gate 0b (owner to confirm).** Invariant (1) as phrased says "all five", but `rx-005` and `rx-009` are `active`, `needsReview: false`, and have no `brandName` — the seed's own generic-only dispensings, which the approved proposal already allowed ("brand name may also be absent for a generic-only dispensing"). Guard S asserts the four clinical fields (`strengthMg`, `frequencyPerDay`, `startDate`, `doseTimes`) on every active unflagged prescription and treats `brandName` as optional throughout. If the owner wants `brandName` mandatory instead, the seed needs brands for `rx-005` and `rx-009`.

## Architecture decisions taken in Phase 0 (approved at Gate 0)

### D-001 · `tokens.css` does not exist in the artifact; WP0 compiles it — approved at Gate 0
The artifact serves `tokens.json` and `bundle.css`; `bundle.css` reads `--navy`, `--space-3`, `--radius-md`, `--shadow-sm`, `--font-sans` and its own structural `--wsf-*` variables. WP0 generates `styles/tokens.css` from the repository copy `docs/design-system/tokens.json` (colour, spacing, radius, shadow custom properties, one utility class per type style, **and `--font-sans`**, the one variable `bundle.css` reads that neither file defines — `docs/design-system/README.md` now says so explicitly; the stack's first family name must stay `"IBM Plex Sans Arabic"` whether loaded from Google Fonts or self-hosted) with a script, so the token file remains the single source. Tailwind's theme maps to those custom properties; no hex, px size or px radius appears in `components/` or `app/`.

### D-002 (approved at Gate 0 with two conditions) · The data layer is a set of server actions over an in-memory mock store; the session is a cookie
`lib/session/api.ts` declares the 5 session signatures and `lib/data/api.ts` the 50 data-access signatures (SCREENS.md appendix). `lib/data/index.ts` and `lib/session/index.ts` (`'use server'`) implement them by delegating to `lib/data/mock/*`, which holds the seed transcription, the schedule generator output and the mutable in-memory state (accepting an invitation, requesting a refill, connecting a chat). The session is an httpOnly cookie carrying subject id, role and linked patient id, read by middleware and shell layouts. Screens — server or client components — call the data functions and nothing else; no component contains `fetch` or imports from `lib/data/mock`. Phase 2 replaces `lib/data/mock/*` behind the same `index.ts`. Mutations survive for the life of the dev server process only, which is within "no persistence beyond local/mock state". **Owner's conditions (Gate 0, approved):** the mock store is a module-level singleton with an explicit `reset()` used by the tests, and **no client component reads it** — every read crosses the seam as a server action. The store's volatility is acceptable; the shape of the seam is not negotiable. Dev-only fault injection (loading delay, error, offline, fixture states such as `onboardingCompleted:false`) is a cookie read **only inside the mock implementation**, so no screen branches on it.

### D-003 (approved at Gate 0) · Copy catalogue and BACKEND-NOTES are split per bundle to honour "two subagents never own the same file"
`i18n/copy/<bundle>.ts` per work package, merged by `i18n/index.ts` (owned by WP1); `docs/backend-notes/<bundle>.md` fragments per bundle, merged into `docs/BACKEND-NOTES.md` by the lead at each gate. Every catalogue key is marked `placeholder: true` until the owner's copy deck replaces it; Arabic placeholders start from the wireframe boards' text where it does not break §13, English is drafted by the build.

### D-004 (approved at Gate 0) · Multi-line reviewer input uses `TextField`
The reviewer's optional note and the return-to-clinic reason are single-line `TextField`s; the system has no textarea and none is invented. Reported as a minor gap, not a blocker.

### D-005 (lead decision, Gate 0b) · Record ids and the mock session cookie are deterministic conventions, never displayed
The seed fixes ids for prescriptions (`rx-001`…) and alerts (`ia-001`…) and none for people or the other records. Ids are technical identifiers (G9: never shown), so assigning them is a build convention, not a seed value; it is fixed here so tests, the e2e helper and the round-trip fixture agree: `Patient.id` `pt-01…pt-04` in cast order (حمد · فاطمة · سارة · بدر) · `Account.id` `acc-01…acc-11` in the seed table's order · `Caregiver.id` `cg-01…cg-08` in the seed table's order · `MessagingLink.id` `ml-01…ml-05`, `PushSubscription.id` `ps-01…ps-04`, `RefillRequest.id` `rf-01` (rx-003, requested) and `rf-02` (rx-001, approved), `CalendarSubscription` keyed by `pt-03` · `Dose.id` = `<prescriptionId>-<YYYYMMDD>-<HHmm>` (deterministic from the generator) · `AuditEvent.id` `ae-001…` in `createdAt` order. The mock session is the httpOnly cookie `jurah.session` holding URI-encoded JSON `{ subjectId, role, linkedPatientId?, pendingInvitationOnly? }` — never a Civil ID — written by `signIn`/`chooseRole`/`acceptInvitation`, read by `getSession`, `proxy.ts` and the shell layouts. `tests/e2e/helpers/session.ts` mints it for the role walks. Listed in BACKEND-NOTES §2 (a client-readable role is a mock shortcut the backend must refuse).

### CR-030 · `TabBar` accepts no single-item set, but a single-clinic-role account has exactly one destination — `DEFAULT` (raised by WP3 at Gate 3)

### D-006 (lead decision, Gate 3) · A signed-in session on a wrong-role route redirects to `/gate`, never to sign-in
The spec states the redirect target only for the no-session case (`/signin`, or `/clinic` for clinic paths). ### D-008 (lead decision, Gate 3) · `useSearchParams` is always consumed under a Suspense boundary
`next build` fails prerendering any statically renderable route whose client tree calls `useSearchParams()` outside `<Suspense>` (`missing-suspense-with-csr-bailout`; the signin pages hit it). `LanguageSwitch` therefore wraps its query-aware link in `Suspense` with a pathname-only link as the fallback. Standing rule for every future bundle: no bare `useSearchParams` — wrap it, with a fallback that keeps the control visible.

### D-009 (lead decision, responsive pass) · The 880px cap applies from 834px, and the boards drawn at 1280 are keyed to content width, not to the 1440 token

### D-014 (lead proposal, handoff-notes audit) · Four places where the mock does not refuse what BACKEND-NOTES §3 said it refused — `DEFAULT`
**What the documents say.** `lib/data/index.ts`'s header: every function re-checks the session before returning anything. BACKEND-NOTES §3 said `getAlertForReview` gates on queue membership, `savePrescriptionDraft` returns nothing for a non-owning session, `readLastKnownSnapshot` is covered by the pending-only rule, and `requestRefill` acts only on a prescription the patient owns. The Phase 2 spec makes each a server-side refusal.
**What the code does.** (1) `getAlertForReview` checks only `role === 'reviewer'` and that the alert exists — `getAlertForReview('ia-002')` (سارة's already-reviewed alert) returns her full patient context. (2) `savePrescriptionDraft` never calls `session()`: any session can write a `Prescription` and its doses for any `patientId`, with the audit row attributed to the patient. (3) `readLastKnownSnapshot` reads a module-level cache with no session check and returns whatever `getPatient` cached for any subject. (4) `requestRefill` finds the prescription by id alone — `requestRefill('pt-01', 'rx-008')` as حمد succeeds and writes a refill row for سارة's prescription under his id.
**Why it matters.** None is reachable from the interface (no screen offers the call), so Phase 1's *absence* holds and no acceptance criterion fails. **Proposal.** Four small guards in `lib/data/index.ts`, each mirroring a check the file already makes elsewhere: (1) return `empty` unless `alert.reviewStatus === 'pending_medical_review'`; (2) `if (!isSelfPatient(s, patientId)) return` the same not-found shape the other mutations use; (3) key the cache by session subject or check the caller's session before returning another subject's key; (4) add `rx.patientId === patientId`. §5's recorded shapes do not change (the generator calls each with an owning session and a pending alert). **Cost:** a unit test per guard; no screen change. **If we don't:** the notes now say plainly that the mock does not enforce these — Phase 2 must build the refusal from the spec, not from the mock. Continued as written (docs corrected, code untouched) pending the owner's answer.

### CR-039 · X0 cannot actually refuse a patient/caregiver-only ID or a pending-invitation-only one — existing cross-bundle infrastructure redirects first — `DEFAULT` (raised by WP4 bundle i, demonstrated live)
- **What the documents say.** SCREENS.md's X0 row and this bundle's own ACCEPTANCE criterion: "a non-clinic ID is refused here with the same neutral wording as A1's `no_claims`"; explicitly "for both an accountless and a patient-only ID."
- **Why it is a problem, demonstrated.** `signIn` writes a session cookie for `pending_invitation_only` and `single_role`/`multiple_roles` outcomes as part of the SAME request that resolves the call (`lib/session/index.ts`). Setting a cookie inside a Server Function lets Next.js return freshly server-rendered UI for the current route in that one round trip (documented at `node_modules/next/dist/docs/01-app/03-api-reference/04-functions/cookies.md`: "After you set or delete a cookie in a Server Function, Next.js can return both the updated UI and new data in a single server roundtrip"). Two pieces of EXISTING, cross-bundle infrastructure react to that fresh cookie inside that same round trip, before this screen's own client code (`resolveDestination`) ever runs: **`proxy.ts`'s `pendingInvitationOnly` rule** (redirects to `/invitation`) and **the clinic layout's own `isEntry` check** (`app/[locale]/clinic/layout.tsx`, redirects a non-clinic session to `/gate`, which A0 then resolves to that role's own shell) — both outside this bundle's files (`proxy.ts` is repository-wide; the layout is explicitly "do not edit" in this bundle's brief). Reproduced live against a running dev server (network trace, not a guess): `POST /ar/clinic` (the sign-in action) → `GET /ar/gate` → `GET /ar/app` for حمد's patient-only ID, entirely within the same second — well before the ~2.1s Hawiati countdown this screen still shows even completes. For ناصر's pending-invitation-only ID the trace is `POST /ar/clinic` → `POST /ar/invitation` → lands on `/ar/signin` (a further, separate issue inside F0's own page, bundle h's — not investigated further here, out of scope for this bundle).
- **What this bundle did about its own share of the bug.** An earlier version of `ClinicSignInForm.tsx` called `signOut()` after detecting a non-clinic outcome, intending to "clean up" the session `signIn` had written. Since the browser had by then usually ALREADY been redirected (by the infrastructure above) to the person's own legitimate shell, that `signOut()` call fired against THAT page instead — actively signing a correctly-arrived patient back out, bouncing them a second time to `/signin`. That active harm is now removed (`resolveDestination` no longer calls `signOut` for these three outcomes); the refusal UI these branches set is left in place as the intended behaviour for if/when the redirect above is fixed, but it is not observed today (`tests/e2e/clinic.spec.ts` documents the actual reachable behaviour rather than asserting the specified-but-unreachable one, with a comment pointing here).
- **Proposal.** The fix belongs to whichever bundle owns `proxy.ts` and the clinic layout (WP3): either the layout's `isEntry` redirect and `proxy.ts`'s clinic-path rule need to recognise "this session was written by the in-flight sign-in attempt this same request is resolving" and defer to X0's own client-side outcome handling instead of pre-empting it, or X0 needs a way to learn the outcome WITHOUT `signIn` committing a cookie the surrounding infrastructure reacts to mid-flight (a seam change, since no such "preview" function is published). Given `proxy.ts` is unowned by any single WP4 bundle and the clinic layout is explicitly off-limits to this one, this is reported rather than fixed here.
- **Cost.** A cross-bundle architecture change (redirect-timing logic in shared, previously-considered-settled infrastructure), not a one-line fix.
- **If we don't.** X0's refusal is observable only for an accountless/no-account Civil ID (`no_claims`, which writes no cookie and is therefore unaffected) — confirmed passing. A patient-only, caregiver-only, or pending-invitation-only ID typed at the clinic door is silently and correctly routed into that person's own legitimate shell instead of being refused, which is not a security hole (nobody reaches clinic data who should not) but does not match the specified wording-parity behaviour.
- **Default until answered.** `features/clinic/ClinicSignInForm.tsx` keeps the refusal-UI code path for all four outcome kinds (in case the upstream redirect is loosened later) but no longer calls `signOut`, and `tests/e2e/clinic.spec.ts` asserts the actual current behaviour for the patient-only case, tagged `(CR-039)`.
- **Doc to update on approval.** SCREENS.md's X0 row / this bundle's ACCEPTANCE wording, once the owner decides which side changes.

## Gate B · AP-10 · Screening on every path (docs/AGENTS-POLISH-PLAN.md § 7.3)

### CR-088 · A retry record for screening requests n8n did not accept — `PROPOSED` (AP-10, 2026-09-24; needs a production migration, so not built)
**What the documents say.** Plan AP-10 step 2: "a screening request that n8n does not accept is not lost: raise a change request for a small retry record (a table or a job), and until it is approved, log the miss where Hamad can see it." **What is built instead, today.** `lib/data/pg/screening.ts` `screenOrHold` holds a prescription whose request n8n did not accept: one `warning` / `pending_medical_review` alert on it, empty citation, raised through the agent's audited insert (`alert_raised`, actor `agent`), so the miss is in the reviewer's queue and the patient's Safety list, plus a `console.warn` line in the server log. If even the hold cannot be written, a `console.error` line (`[screening] NOT SCREENED AND NOT HELD: prescription <id>`) is the only record. **Why that is not enough.** A hold is a person's work item, never retried by the system; a job n8n accepted and then failed to finish leaves no record in the app at all; and the "being checked" state (CR-089) can only approximate "not answered yet" with a time window. **What is proposed.** One migration, `0015_screening_requests` (0014 is now AP-12's `0014_audit_insert_actor.sql`; renumber if another package takes 0015 first), one new table, no change to any existing table:
```sql
create table if not exists screening_requests (
  id               text primary key,
  patient_id       text not null references patients (id),
  prescription_id  text not null references prescriptions (id),
  trigger          text not null check (trigger in ('saved', 'agent_saved', 'field_confirmed', 'refill')),
  requested_at     timestamptz not null default jurah_now(),
  attempts         int not null default 1 check (attempts between 1 and 5),
  accepted_at      timestamptz,
  answered_at      timestamptz,
  held_alert_id    text references interaction_alerts (id),
  last_error       text check (last_error is null or char_length(last_error) <= 200)
);
create index if not exists screening_requests_open on screening_requests (requested_at) where answered_at is null;
alter table screening_requests enable row level security;
-- jurah_agent only (the role screenOrHold and /api/agent/alerts already run as); no policy and no
-- grant for jurah_app, so no patient, caregiver, reviewer or admin session reads or writes a row.
grant select, insert, update (attempts, accepted_at, answered_at, held_alert_id, last_error) on screening_requests to jurah_agent;
create policy screening_requests_agent_all on screening_requests for all to jurah_agent
  using (true) with check (trigger in ('saved', 'agent_saved', 'field_confirmed', 'refill'));
```
`screenOrHold` inserts the row before it calls n8n and sets `accepted_at` when n8n accepts; `POST /api/agent/alerts` sets `answered_at` on the open rows of every prescription an alert names; a job route `POST /api/jobs/retry-screening` (job bearer, beside `expire-invitations`, a Vercel cron every 10 minutes) re-sends rows with `accepted_at is null`, or unanswered after 15 minutes, up to 5 attempts, then raises the hold. The retry record also makes CR-089 exact: being checked = an open row. **What it costs.** One migration applied to production by the lead, one job route, one cron line, the two small writes above, their unit and integration tests. **What breaks if we don't.** Nothing silently: every miss is still held or logged. But a hold waits for a person, and an accepted job that dies inside n8n is visible only in n8n's execution list (AP-18's error workflow is the other half).

## Gate B · AP-18 · Robustness (docs/AGENTS-POLISH-PLAN.md § 7.3)

### CR-104 · The Alexa request signature is not verified — `PROPOSED` (raised by AP-18, 2026-09-24)
**What the documents say.** `agents/README.md` names the gap: `agent-alexa` checks the skill id and the 150-second timestamp window but never the request signature, so a request that merely names the right skill id and a fresh timestamp is accepted — the AGENTS-POLISH-PLAN's own finding list carries the same line. Amazon's own certification requirement (read 2026-09-24, "Host a Custom Skill as a Web Service", `https://developer.amazon.com/en-US/docs/alexa/custom-skills/host-a-custom-skill-as-a-web-service.html`): "Web services that accept unsigned or out-of-date requests will not pass certification." Since this skill is read-only (AP-02/CR-073: no dose is ever written from a voice turn) the exposure is a spoofed request reading a patient's schedule and today's status words, not a false dose record — still a Civil-ID-adjacent read the spec does not intend for an unauthenticated caller. **The proposal — two options, neither built.**
**Option A: verify it inside `agent-alexa`.** An HTTP Request node fetches the certificate chain from the request's own `SignatureCertChainUrl` header; a Code node validates it against ONE pinned, hard-coded root (never the runtime's own trust store: n8n Cloud's Code node exposes only the `crypto` Node.js module and `moment`, nothing that reads an OS certificate store — confirmed on n8n's own docs, "Using the Code node", `https://docs.n8n.io/build/code-in-n8n/using-the-code-node`, "n8n makes two modules available for you: crypto Node.js module, moment npm package") and checks the signing certificate's dates, its `echo-api.amazon.com` SAN entry and the chain of `checkIssued`/`verify` calls up to that pinned root; the Webhook node's "Raw Body" option (documented, `https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.webhook`) supplies the exact bytes `Signature-256` was computed over, since Alexa's signature covers the raw HTTP body, not the parsed JSON. Proved locally (Node 24, this machine; a throwaway self-signed chain generated with `openssl` in the session's own scratchpad, never a real Amazon certificate): `node:crypto`'s `X509Certificate` has `checkIssued`, `verify`, `validTo` and `subjectAltName`/`checkHost`, and `crypto.verify('RSA-SHA256', body, cert.publicKey, signature)` correctly accepts the genuine body and rejects a tampered one — see the pasted proof below. **Needs, before it can be built:** `agents/scripts/build.js` free to edit again (the Telegram lane AP-02 → AP-03 → AP-05 → AP-11 is still releasing it, per the plan's own dependency note) and a live proof that n8n Cloud's actual Code-node sandbox behaves as its docs say (this package touches no live system). **Option B: verify outside n8n.** A `src/app/api/**` route receives the Alexa request first, verifies the signature with Node's full `crypto` and `tls` (no module allowlist to work around), then forwards the verified body to `agent-alexa` over the same header-secret pattern every other route already uses. This changes the endpoint registered in the Alexa developer console (Mohammad's account) and needs a new server-held secret between the route and n8n (the owner supplies it, `CLAUDE.md`: "a credential you do not have"). **What it costs.** Option A: no schema change, no new secret, but waits on another lane's file. Option B: no schema change, one new secret, one console change, and a small amount of latency added ahead of Alexa's own timeout budget (agent-alexa already spends part of an 8-second budget on free talk, CR-070). **What breaks if we don't.** `agent-alexa` keeps answering any caller who can guess or observe a linked device's `userId` and the skill id (neither is presented as secret today) with that patient's schedule and dose-status words, indefinitely, on the live skill.

**Not verifiable without the live n8n instance (the lead):** whether n8n Cloud's actual Code-node sandbox permits `require('crypto')` in practice, not only in its docs; whether a trusted-root store is reachable from that sandbox at all (Option A does not need one — the root is pinned from its own public source instead — but confirming `node:tls` is absent, as the docs imply by omission, is a live fact, not a doc fact); whether the Webhook node's "Raw Body" option, once turned on, delivers exactly the bytes `Signature-256` was computed over on a real Alexa request; whether an outbound HTTP Request node in that same workflow can actually reach `s3.amazonaws.com` from n8n Cloud's network. The demo limits stay written in `agents/README.md` (a pointer to this entry added there) until one option is chosen and built.

### CR-105 · `Settings.notificationChannel` and how a patient ever gets `'telegram'` — `PROPOSED` (raised by AP-18, 2026-09-24; the built half is `ACCEPTED by the lead session under the owner's instruction of 2026-09-24 to run the plan end to end`)
**What is built and proven (`node --test`/`vitest`, pasted in `docs/backend-notes/ap-18.md`).** `lib/agent/notify.ts`'s `deliverAlert` now reads `recipientsFor`'s new `notificationChannel` field before sending the PATIENT'S OWN Telegram message: `'none'` and any value the column cannot hold (both normalised to `'none'` in `lib/data/pg/agent.ts`, never guessed at in `notify.ts`) send nothing; `'whatsapp'` and `'email'` send nothing either, because neither has a transport yet, so the code fails closed instead of guessing a channel; only `'telegram'` sends. This never gates an ACTIVE caregiver's chat (no `settings` row exists for a caregiver at all — `AI Agents Acceptance Criteria.md` line 193: "an active caregiver's chat receives alerts") and never gates push (`types/contracts.ts` line 224: `notificationChannel` is "the CHAT channel" only; push stays governed by the granted subscription alone). **The problem this does not close.** Nothing in the product sets `notificationChannel` to `'telegram'` today: no screen offers the control (D-041 in this file: "no channel control on E3"), and `connectMessagingLinkByToken` (`lib/data/pg/channels.ts`) writes only the messaging link and its audit row. Every patient therefore reads the column's default, `'none'`, for as long as that stays true — including seed pt-03, whose `lib/data/mock/seed.ts` row is hand-set to `'telegram'` for the demo, a fact the database does not yet reproduce on its own. **The proposal.** Connecting Telegram (the existing `/start`-token flow, D11/CR-083) should also set `notification_channel = 'telegram'`, and disconnecting should reset it to `'none'` — the same event already writes the link and its audit row, so the channel would change alongside it, never on its own. **The gap this proposal runs into.** `connectMessagingLinkByToken` runs under the system actor (`withSystem`), and `supabase/migrations/0005_rls.sql` grants the system session UPDATE on `settings` (line 260: `settings_update_own ... or jurah_session_is('system')`) but not INSERT — only a patient's own session may INSERT a first row (lines 257-258: `settings_insert_own ... jurah_session_is('patient')`). A patient who already has a `settings` row (every seed patient except the D-041 demo pair) could have its channel updated this way; a patient with none could not — connecting would need to run as a patient-session write instead (a contract change to where `connectMessagingLinkByToken` is called from), or the system session's INSERT grant would need widening, or a migration would need to backfill a default row for every patient. Which of these — the owner's call; nothing here is built. **What it costs.** The read-side fix above: no schema change, no owed value. The open proposal: no schema change either way, but the INSERT-grant or backfill option is a policy change (`CLAUDE.md`: "never write `using (true)`", "every write policy needs a `with check` clause" — a widened grant would need the same scrutiny CR-091 already gave the audit-insert policy). **What breaks if we don't.** Merging this package's read-side fix, by itself, changes who receives a Telegram alert today: a linked patient whose PRODUCTION `settings.notification_channel` row already reads `'none'`, or who has no row at all (the two D-041 demo patients), stops receiving the Telegram alert `deliverAlert` used to send them unconditionally — their push and any caregiver's alert are unaffected. This is the correct reading of the spec (`AI Agents Acceptance Criteria.md` line 193), not a regression, but it is a visible behaviour change on the live database that the lead should read before merge: which linked, demo-relevant patients currently read `'telegram'` in production (seed pt-03 should; nothing else is known to).
