## §4. Fields B1/B2 are blank without

- **`Dose.tracked`** — B1/B2's entire safety claim rests on this field being set correctly *at generation time* (already flagged in `docs/backend-notes/wp2b.md` §4, repeated here because this is the screen that would silently look right and be wrong: a generator bug that leaves `tracked` unset — rather than explicitly `false` — on an untracked patient's doses shows a pill it must not, because the contract's default is `true`).
- **`Prescription.discontinuedReason` / `discontinuedAt`** — B2's past group has nothing else to say about a discontinued prescription. Absent, the card falls back to the bare "Completed" wording even for a `discontinued` record (no crash, no "undefined" — but a materially less useful past list).
- **`InteractionAlert.sourceCitation`** — B2 passes it straight into `InteractionAlert`'s `description`-adjacent slot only via the alert record itself; the placeholder `[TO BE SUPPLIED]` (`ia-001`) renders verbatim, matching `docs/DECISIONS.md` CR-014's row for `AlertDanger.dc.html`/`ReviewerDecision.dc.html`.
- **`Settings.adherenceCheckInEnabled`** (or its absence — بدر has no `Settings` row) — both screens read it once per render (`tracked`) to decide whether *any* status pill may show anywhere on the screen, regardless of what an individual `Dose`/next-dose lookup carries. A patient with no `Settings` row must resolve to the documented default (`false`) — already true via `getSettings`'s own fallback — never to a crash or an implicit `true`.

## §7. Things this work found out the hard way

1. **`lib/data/mock/faults.ts`'s own doc comment invites "WP4's screens" to read it directly, but guard 3 (the seam) refuses any import of `lib/data/mock/**` from outside `lib/data/`/`lib/session/`/`tests/`.** `docs/briefs/WP1.md`'s own text ("a cookie … read only inside `lib/data/mock/faults.ts`; nothing else branches on it") reads, on a second pass, as a statement about what WP1's *own* code does — not a licence for a screen to import it — and guard 3 settles the question either way: it is a hard failure, not a style nit. B1/B2 instead demonstrate their G7 loading/error/failed-refresh states with a **self-contained, dev-only `?view=loading|error|offline` query flag**, read once from each page's own `searchParams` prop (never `useSearchParams`, D-008) and nowhere else — no fetch, no mock import, no seed data of its own. It is not a documented product feature; a future bundle wiring the same states elsewhere should either repeat this pattern or (better) get `faults.ts` genuinely exported through `lib/data`'s own barrel so guard 3 stops disagreeing with its own file's doc comment.
2. **`PrescriptionCard`'s `doseTimeLabel` only renders when `dose` is also supplied** (`components/ui/PrescriptionCard.tsx`: the whole dose row is gated on `{dose ? (...) : null}`). B2's own acceptance criterion — "the next/most-recent dose status **only when tracked, otherwise the next dose time**" — has no way to be met literally with the shipped component: there is no prop shape that shows a bare time with no status pill. `MedicinesList` omits the dose row entirely for an untracked patient's card (never a status word, never an invented pill) rather than patching `components/ui/**` (out of this bundle's file list). Reported, not fixed here; a future revision decoupling `doseTimeLabel` from `dose` would close this cleanly. Filed as a needed-change request against `components/ui/PrescriptionCard.tsx`.
3. **`PrescriptionCard` takes `onOpen: MouseEventHandler`, not an `href`** (unlike `DoseRow`/`Card`, which render a real `<a>`). `features/day/PrescriptionCardLink.tsx` is a one-line `'use client'` wrapper reusing the exact `router.push` pattern `features/shell/NavigateButton.tsx` already established elsewhere in the repo, so `MedicinesList` can still honour its `hrefBuilder` contract. Not a design-system edit; a future `href` prop on `PrescriptionCard` (matching `Card`'s own `href`+`as="a"`) would make this wrapper unnecessary.
4. **No design-system component exists for a de-emphasised "past prescription" row with a discontinuation reason and date** — `PrescriptionCard.md`'s own contract has no slot for either field, and the board itself (`MedicinesPast.dc.html`) hand-rolls a plain block for exactly this reason rather than using `PrescriptionCard`. B2's past group is composed on the bare `Card` (a generic surface, not a specific molecule — `Card.md`: "any self-contained block") with plain text lines, per CLAUDE.md's rule that a *missing* component is reported, never invented inline; this is not a new component, only a different composition of an existing generic one. If the owner wants a dedicated past-prescription molecule, that is a WP2/Build-Prompts follow-up, not something invented here.
5. **The seed has no patient with two simultaneous alerts**, so B2's "multiple alerts (lead with most severe, link the rest)" state cannot be walked end-to-end against real seed data without inventing a second alert for a real patient — forbidden (CLAUDE.md: never invent a seed value). It is exercised instead in `tests/unit/day/MedicinesList.test.tsx` (two alerts passed directly to the presentational component) rather than in `tests/e2e/day.spec.ts`. If the owner wants this walkable end-to-end from a seeded sign-in, that is a `docs/Seed Dataset.md` change request, not a build decision.
6. **The `?day=` boundary rules.** Absent `?day=`, B1 reads `REFERENCE_DATE` (never `Date.now()`); an invalid or malformed value (anything not matching `/^\d{4}-\d{2}-\d{2}$/`) falls back to `REFERENCE_DATE` rather than erroring — day navigation itself only ever produces valid values (`lib/schedule/dates.ts`'s `addDays`), so the fallback exists solely against a hand-typed or stale URL. Nothing about a specific date is validated against a prescription's own `startDate`/`durationDays` window at the routing layer — that is `lib/schedule/generate.ts`'s job (already built, unedited here), which simply returns no rows for a date outside a prescription's window.
7. **The duration-boundary derivation is entirely `lib/schedule/generate.ts`'s (unedited).** B1 does nothing special to make `rx-002`'s 2026-09-25 boundary visible — it is a plain consequence of `getDosesForDay` returning fewer rows on 2026-09-26. `tests/e2e/day.spec.ts` asserts the row count (3, not 6) and the absence of "Ibuprofen" in the dose list on that date, rather than asserting on a boundary-specific UI affordance, because there isn't meant to be one — the schedule simply stops listing a dose once its prescription's window has closed.
8. **`LastKnown`'s "as of" line uses `REFERENCE_NOW` directly, not a real snapshot of B1/B2's own data.** `lib/data/index.ts`'s `recordSnapshot`/`readLastKnownSnapshot` machinery is currently only wired for `getPatient` (`docs/backend-notes/wp1.md` §2), not `getDosesForDay`/`getPrescriptions`/`getAlerts` — and `lib/data/index.ts` is out of this bundle's file list (`lib/**`). B1/B2's `?view=offline` state therefore re-fetches the current (always-succeeding, in-memory) data and wraps it in `LastKnown` with `asOf: REFERENCE_NOW`, which is honest about what the mock can actually demonstrate (there is no real failure to recover from) but is not a working "last known, possibly stale" snapshot the way H3's own offline page is for `getPatient`. A future bundle wiring real snapshot recording for these two functions in `lib/data/index.ts` would let this become a real stale-vs-fresh distinction.
9. **`copy.day.discontinuedOnTemplate`/`discontinuedReasonTemplate` interpolate `Prescription.discontinuedAt`/`discontinuedReason` verbatim — the latter is raw seed/data text, not a copy-catalogue string, and is never translated by locale** (rx-004's reason is written in Arabic in the seed; it renders identically on the English screen). This matches how every other data-derived string in the product behaves (drug names, facility names) and is not a bug; noted because it is easy to mistake for a missing translation.
