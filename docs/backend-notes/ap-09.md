## What changed

- **One way in.** `POST /api/messaging/telegram/open` (`app/api/messaging/telegram/open/route.ts`)
  replaces F1's `GET` (commit 2a3c901, cherry-picked first, then replaced; `GET` now answers `405`).
  A same-origin form post (the `Origin` host must equal `x-forwarded-host` or `Host`, the check Next
  makes for a Server Action; a missing or `null` Origin, or a `Sec-Fetch-Site` other than
  `same-origin`, is refused) from a patient or an `active` caregiver mints the person's own link
  through `startMessagingLink` and answers `303` to `https://t.me/<bot>?start=<token>`. The token is
  only in that `Location` header. Everything else is a `303` back to the screen with no token. While
  the bot is simulated (no `JURAH_BOT_TOKEN`), the link is minted and the answer goes back to the
  screen; nothing is ever sent to a `t.me` address then. If Telegram does not name the bot
  (`getMe` fails), nothing is minted. `Cache-Control: no-store` and `Referrer-Policy: no-referrer`
  on every answer; `next.config.ts` gains a path rule because the site-wide
  `strict-origin-when-cross-origin` replaced the route's own `Referrer-Policy` (seen in the first
  local curl, below).
- **The link-token rules are unchanged.** `lib/data/pg/channels.ts` is not in the diff: single use,
  15 minutes, one live token per subject, the caregiver trigger.
- **One form.** `features/ambient/TelegramLinkForm.tsx`: the design system's `Button` inside a plain
  `<form method="post">` with two hidden fields, `locale` and `from` (`notifications`, `setup`,
  `profile`; the route maps them to fixed return paths, so there is no open redirect). A real bot:
  `target="_blank"`, so this tab stays and waits. Simulated: it posts in place. Used by E5 (not
  connected, expired, the iOS "chat instead", pending "open again"), A2's Telegram offer and F4.
  No screen calls `startMessagingLink` any more.
- **The page never holds the token.** E5 and F4 pass `linkForScreen(link)` (`lib/messaging/link.ts`)
  to their client components, which drops `linkToken` and `chatId` on the server. Before, the whole
  `MessagingLink` was a client prop, so a pending link's token was in the page's RSC payload (proof
  below).
- **The waiting state (CR-087).** `useLinkConfirmation`: every 3 s for 5 minutes (the token lives
  15), at once when the person comes back to the tab, and on "I pressed Start" (ضغطتُ «ابدأ»), which
  restarts the five minutes and, when the link is still waiting, says so in one quiet
  `role="status"` line. After five minutes the notice says the page stopped checking by itself. E5
  and F4 both; F4's pending row had no action and did not poll at all before.
- **Mock parity with the database.** The mock's `startMessagingLink` now refuses a caregiver who is
  not `active` (the trigger `link_caregiver_must_be_active`), its auto-confirm connects only a
  still-pending row of an active subject (as `connectByToken`), and it spends the token on connect.
- **One mock store per server process.** The first full e2e run failed on حمد's round trip: the
  route answered its 303, and E5 still read "not connected". Next bundles a route handler apart from
  the pages, and `lib/data/mock/store.ts` kept the store in a module-level `let`, so the route minted
  into its own copy. The store now lives on `globalThis`, and live audit and link ids are counted
  from the store (a counter per module copy would issue one id twice).
  `tests/unit/data/mock-store-shared.test.ts` proves both with two module copies. Mock only: the
  database was always shared.
- **Copy.** Four lines in `i18n/copy/ambient.ts` (`e5ChatCheckAction`, `e5ChatOpenAgainAction`,
  `e5ChatStillWaiting`, `e5ChatStoppedChecking`), Fusha, no em dash, each locale its own language,
  `placeholder: true`, reused by F4.
- **Documents.** `docs/API-SURFACE.md` §B lists the route (and says it is the one route a screen
  reaches); `docs/BACKEND-NOTES.md` and `docs/BACKEND-DIVERGENCES.md` D-12 describe the new path.
