# WP4 bundle e — Safety list + alert detail (C1, C2): notes

## §2. Where the mock cheated

- **`getAlert`/`getAlerts` are plain array reads with no transaction boundary of their own.** `lib/data/index.ts`'s `getAlert`/`getAlerts` (not this bundle's files — read-only) find-and-return an `InteractionAlert` row from the in-memory store; there is no read/write lock, no optimistic-concurrency token, nothing that could race with a reviewer's `submitReviewDecision` mid-read. Phase 1 has no concurrent writer to race against (the reviewer flow is a separate, unbuilt clinic bundle), so this has never been exercised; Phase 2's real API should still guarantee a read returns a consistent snapshot even while a reviewer's write is in flight.
- **`InteractionAlert.sourceCitation` is a single un-localised string, exactly like `Prescription.discontinuedReason`, `AuditEvent.message` and every other free-text data field this build has met.** C2 renders it verbatim regardless of `locale` (English and Arabic sessions see the same Arabic citation text when one exists) — this is the seam's existing behaviour (`MedicinesList`/`CaregiverAlertDetail` already do the same for `description`), not something this bundle introduced or could fix without a contract change (a per-locale citation field, which no document asks for).

## §3. Rules that are currently absences, and must become refusals

|---|---|---|---|

## §4. Fields C1/C2 depend on, and what renders instead when they are absent

- **C1** (`features/safety/SafetyList.tsx`) needs `InteractionAlert.severity` and `.reviewStatus` for every row's `AlertRow`, and resolves `.involvedPrescriptionIds` through `getPrescription` to build each row's drug-name headline; a prescription id that fails to resolve (deleted, inaccessible) is simply left out of that row's `drugs` array rather than breaking the row — `AlertRow` renders an empty headline (`''.join(' + ')`) in the pathological case of zero resolved names, which never happens against the current seed (every alert's prescriptions resolve).
- **C2** (`features/safety/AlertDetail.tsx`) needs `severity`, `reviewStatus`, `description` for the `InteractionAlert` banner itself; `reviewerDecision`/`reviewerNote`/`reviewedAt` are each rendered through `DetailRow`, which already turns `null`/`undefined` into its own em-dash rather than "undefined" — so a `reviewed` alert missing one of these (a data-entry gap, not a designed state in this seed) degrades to an em-dash row, never a crash. `sourceCitation` is treated as absent for both `undefined`/empty-string *and* the literal `TO_BE_SUPPLIED` marker (see §7). Without any resolved `Prescription` at all (every id in `involvedPrescriptionIds` fails to resolve) the "involved prescriptions" section renders its heading with zero cards beneath it — a plain, honest empty section, not an error; this never happens against the seed (`ia-001`/`ia-002`/`ia-003` each resolve every one of their prescriptions).

## §7. Things this work found out the hard way

1. **`sourceCitation` is `TO_BE_SUPPLIED` for all three seeded alerts, not just `ia-001`.** `docs/Seed Dataset.md` and `docs/DECISIONS.md` (CR-014) discuss the owed citation specifically for `ia-001` (the Warfarin × Ibuprofen finding, the one a clinician would actually query a drug database for); the brief that started this bundle likewise expected "`ia-002`/`ia-003` render their seeded citations verbatim" as a distinct, already-real-valued state. `lib/data/mock/seed.ts` (not this bundle's file) in fact sets `sourceCitation: TO_BE_SUPPLIED` on **all three** alert rows (lines 274, 280, 289), with `ia-002`'s own comment confirming this is deliberate: "not stated for ia-002 either — same 'never invent' rule". **Nothing here was changed to compensate** — this bundle builds the general rule correctly (an empty/`TO_BE_SUPPLIED` citation renders the honest "unverified" line from `copy.safety.c2SourceUnverified`; any real citation string would render verbatim, exercised in `tests/unit/safety/AlertDetail.test.tsx` with a synthetic fixture string), and today that rule fires for all three real alerts rather than only `ia-001`. This is a **fact about the current seed**, not a bug in this bundle, and is worth the owner's attention only if the intent was ever for `ia-002`/`ia-003` to carry a real citation already — nothing in `Seed Dataset.md`'s prose says so, so no `docs/DECISIONS.md` entry was logged for it (this bundle owns no file under `docs/**` besides this one).
2. **`InteractionAlert.reviewedBy` has no published way to become a display name.** `ia-002.reviewedBy` is `'acc-10'` (د. خالد's `Account.id`, per CR-028's own default), and `getAlert` returns the raw `InteractionAlert` contract shape — `reviewedBy` crosses the seam completely unresolved. No function in `docs/SCREENS.md`'s appendix (the 55-function published surface) turns an `Account.id` into a name, and this bundle owns no file under `lib/**`/`types/**` to add one. This is the same shape of gap CR-031 named for F4's own caregiver name, so this bundle followed that precedent rather than inventing a resolution path: `AlertDetail.tsx` never reads `alert.reviewedBy` at all, and renders a fixed role label ("a medical reviewer" / `copy.safety.c2ReviewerValue`) for the "who" `DetailRow` instead of a name. **Needed change, for the owner or a WP1 follow-up:** either add a resolved, Civil-ID-stripped display name to `getAlert`'s return shape (a view type carrying `reviewedByLabel: string`, resolved server-side, never the raw id) for `reviewed` alerts, or confirm that a role label is the intended rendering and update `docs/Acceptance Criteria and Test Plan.md`'s C2 row accordingly (it currently only says "human label per CR-028", which this rendering satisfies literally but perhaps not as the owner pictured it — CR-028 itself says "the seed row is read as 'the account holding that Civil ID'", which reads more like an intent to resolve a name than to substitute a role word).
3. **C2/F3 parity note, for the lead's reconciliation (per this bundle's brief).** `features/caregiving/CaregiverAlertDetail.tsx` (bundle h, read-only, not touched here) renders the same `getAlert`/`getPrescription` pair but noticeably less than this bundle's C2: it shows the three-part danger-only Card (risk/action/who as three separate labelled lines, duplicating text `InteractionAlert` already renders once via its own `description` and `reviewStatus` copy) and the citation, but **never** the `reviewed` state's decision/note/who block at all — a caregiver opening `ia-002`-shaped content today sees no `reviewerDecision`, no `reviewerNote` and no "who reviewed it" anywhere, even though SCREENS.md's F3 row promises "each renders identically to the patient's own view minus every action." This bundle's C2 is the fuller, spec-correct rendering (three-part shape scoped to `danger` + `pending_medical_review` only, per UX Principles §8's own definition of a danger-severity finding; a separate `reviewed` block for any severity). Recommendation: F3 should render the same missing `reviewed` block C2 now has (decision/note/who), and could drop its own duplicated three-part Card in favour of relying on `InteractionAlert`'s built-in copy the way this bundle does — but that file belongs to bundle h, so nothing there was changed.
4. **`sourceCitation`'s honesty check treats an empty string and the `TO_BE_SUPPLIED` marker identically**, on purpose: `AlertDetail.tsx`'s `citationIsUnverified = !alert.sourceCitation || alert.sourceCitation === TO_BE_SUPPLIED`. Nothing in the current seed actually uses a bare empty string for this field (all three are the literal marker), but `docs/SCREENS.md`'s C2 row phrasing ("empty citation shown as unverified") suggested a future seed value might be `''` rather than the marker, so both are handled the same honest way rather than only one.
5. **The Playwright run against the shared dev server (port 3100) intermittently threw `browserContext.close: ENOENT … .zip`/`.trace` errors on trace-artifact teardown** across two full runs of `tests/e2e/safety.spec.ts --workers=1`, on a different random subset of tests each time (never the same assertion twice, never an `expect(...)` failure — always the trace-writer's own file handle). This is the disk/process contention the brief's own environment note warned about (several sibling bundle agents' dev servers and Playwright workers sharing the machine); it was not chased to a clean run per that note's instruction. One real bug was found and fixed in the same pass: `getByText('Warfarin')` was a strict-mode violation (three elements contain that substring — the `h2` title, a drug-line list item, and the `PrescriptionCard`'s own generic-name span); the fixed assertion scopes to `.wsf-rx` cards via `.filter({ hasText: … })`, matching `tests/e2e/day.spec.ts`'s own convention for card-scoped assertions.
