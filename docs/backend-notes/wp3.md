# WP3 — Shells, routing, system pages: notes

## §2. Where the mock cheated

- **The session is a cookie the client can forge.** `proxy.ts` and every shell layout (`app/[locale]/app|care|clinic/layout.tsx`, `features/shell/gate.ts`) trust `jurah.session` at face value — a URI-encoded JSON blob a browser's own dev tools can edit. Nothing here signs it, encrypts it, or checks it against a server-side session store. **The backend must issue the session (on `signIn` / `chooseRole` / `acceptInvitation`) and verify it on every request that reaches a role-gated route or a patient-scoped data call** — a signed, httpOnly, server-verified session (JWT or an opaque id against a session table), never a client-editable role string. Proving request: set `document.cookie` (or a raw `Set-Cookie` via curl) to `{"subjectId":"pt-01","role":"admin"}` and confirm `/clinic/audit` now renders the audit log for a Civil ID that was never an admin — that must fail once Phase 2 lands.
- **The pathname-forwarding headers (`x-jurah-path`, `x-jurah-locale`) are a Phase-1-only convenience**, not a security mechanism: they let a Server Component layout read its own pathname without a client hook, so the clinic shell can tell X0's entry apart from its two destinations. They carry no access decision — proxy.ts's redirects still run first — but a real deployment should confirm no edge/CDN layer strips or spoofs custom request headers before they reach the app server, since the clinic layout's chrome selection (not its role gate) currently trusts them.
- **`requireRole`'s "wrong role but signed in" destination (`/gate`) is a UX nicety, not a policy.** It sends an already-authenticated-but-wrong-shell session to the resolver that already knows its real home, rather than back to sign-in. Phase 2 should keep this behaviour (a real 403 that still lets the client redirect intelligently) rather than a bare HTTP 403 with no next step — the UX principle ("no dead ends") applies to the failure path too.

## §6. Deferred to Phase 2 by design

Nothing new beyond what earlier fragments already recorded — WP3 adds no data function, no real network call, and no new deferred capability. The cross-fade transition between shells (role switch, tab switch) is left to CSS only per the brief; no View Transitions API integration was attempted (recorded in §7 below as a gap, not a Phase-2 deferral, since it is presentational rather than a backend seam).

## §7. Things this work found out the hard way

1. **Sheet's positioned ancestor, confirmed.** `Sheet.md` requires the screen's content root to be `position: relative` so the sheet/modal positions against it rather than the viewport. Every shell wrapper this package built (`AppShell.tsx`, `ClinicNav.tsx`, the no-shell `signin`/`invitation` layouts) sets `relative` on its outermost element for exactly this reason — no bundle that adds a `Sheet` later should need to add its own positioning context.

2. **`TabBar`'s own type refuses a single-item bar, but the clinic shell needs one.** `components/ui/TabBar.tsx`'s `TabBarItems` is `[T,T] | [T,T,T] | [T,T,T,T]` — no one-item tuple. The written brief for the clinic shell is explicit that the bar is "built from the role set, never filtered down": a reviewer-only account should see Review only, an admin-only account Audit only. With only one destination there is nothing to switch between, so `features/shell/ClinicNav.tsx` renders **no** TabBar at all when `roles` yields exactly one destination, rather than inventing a disabled second tab or a fake one-item bar. Filed as a needed-change request in the WP3 report against `components/ui/TabBar.tsx` (its `TabBarItems` union could add a `[T]` member, or the design system could document that a shell with one live destination renders no bar) — not edited here, per `components/ui/**` being out of this package's file list.

3. **`href` vs `onChange` on `TabBar`/`MenuRow`.** Every navigational tab and row in this package's shells is a real `<a href>` (App Router navigation, back/forward, "open in new tab" all work); `onChange`/`onClick` is reserved for the handful of rows that are genuinely actions with no URL of their own (the role switch, sign-out). Nothing here fires `onChange` after `href` navigates — the two are alternatives, not required together, contrary to what `TabBar.md`'s port notes might suggest for a case with client-side `value` state to keep in sync; this package's `value` always comes from the current pathname (server-rendered), so no client sync was needed.

4. **Two special files render with no `params` at all.** `not-found.tsx`/`error.tsx`/`global-error.tsx` in this Next version (see `node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/{not-found,error}.md`) accept no props beyond `error`/`retry` — no dynamic-segment `params`, confirmed against this repo's own vendored docs rather than assumed from prior training. `features/shell/request.ts` (reading the `x-jurah-locale`/`x-jurah-path` headers proxy.ts stamps) is how `not-found.tsx` recovers its locale; `error.tsx` — a Client Component, so it cannot call `headers()` — instead reads the locale from `usePathname()` and its shell home from a client-side `getSession()` call in `useEffect`.

5. **`error.tsx`'s reset function is named `retry`, not `reset`, in this Next version** (a breaking rename this repo's own vendored docs flag: "in most cases, you should use `retry()` instead" of the still-available `reset()`). Built against `retry` throughout; the WP0-era stub this package replaced still used `reset`.

6. **The clinic rail's sign-out control has nowhere canonical to live at phone width.** CR-020 places it "in the app bar's action slot at phone width", but the clinic screens themselves (G1s/G2s/G3s/X1) are still placeholders owned by a later bundle, so there is no shared AppBar in this package's clinic chrome to hold it. `ClinicNav.tsx` instead renders a quiet sign-out control beside the simulated-role banner at phone width (hidden at tablet+, where the rail's own sign-out row takes over) — an interpretation, not a literal reading of CR-020, flagged for the bundle that eventually gives G1s/X1 their own AppBars to reconcile (at that point the phone-width control could move into that AppBar's action slot instead).

7. **A board-versus-spec gap, logged to `docs/DECISIONS.md`:** `ReviewerQueue.dc.html` and `ReviewerDecision.dc.html` omit the TabBar that `FieldQueue.dc.html`, `AuditLog.dc.html` and the written spec (G8: "two destinations … no hamburger, no hidden drawer") all keep. Built from the spec (the TabBar/rail renders on every clinic screen this shell wraps, G1s and G2s included), not from those two boards.
