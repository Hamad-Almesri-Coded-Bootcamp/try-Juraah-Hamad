## One deliberate choice, recorded rather than left silent

`routeInbound` cannot tell an image sent as a Telegram *document* from a PDF sent as a document, because the relay (`lib/messaging/telegram.ts` / `lib/agent/inbound.ts`) forwards a bare `documentFileId` with no mime type at all (confirmed by reading both files; no app change is needed or made here). So a fresh `documentFileId` always enters the same `'photo'` route as an inline photo, and `photoQuestion(mime, buffer)` - run immediately after the file is downloaded, *before* any model call - decides a PDF is `prescription` outright from its mime type (`mimeShortcut`), never spending a Gemini call on it. This reaches the same place the plan's step 2 rule 3 asks for ("a patient's PDF goes straight to extraction"), one hop later than a literal reading of "decided before download" might suggest. Proven by `agents/test/orchestrator.test.js` ("a PDF sent as a document is decided as prescription without asking the model at all") and `agents/scripts/check.js` ("a PDF sent as a document is decided prescription from its mime type alone, never asked to the model").

**One thing this branch does not change, on purpose.** `agents/knowledge/scripts/build.js`'s `TC_CHECK` (Travel Check's own generator, outside this package's reserved files) already answers a backend-unreachable profile with a hardcoded `{ verdict: 'could_not_identify', reason: 'profile_unavailable', appOutcome: { kind: 'could_not_identify' } }` - a different claim from `VERDICT.CANNOT_VERIFY` ("we know the profile, this specific pair is outside our data"): here we do not even know the profile. Its test in `agents/knowledge/scripts/check.js` ("profile unreadable (backend 503)") is left asserting `could_not_identify`, unchanged - checked by hand against `build.js`'s source before deciding not to touch it.
