# WP4 bundle b — Sign-in, role chooser, first-run setup, profile: notes

## §2. Where the mock cheated

- **The Hawiati approval is a client-side timer, not a real identity provider.** `signIn(civilId)` (WP1's session module) already decides the whole outcome — steps 1–4 of `ROLES.md`'s resolution, including writing the session cookie for anything but `not_in_test_list` — the instant it is called. `features/identity/SignInForm.tsx` adds the "open the Hawiati app and approve" ritual entirely on top of that already-decided result: it shows the `Countdown` component running, waits a fixed ~2.1 real seconds (`APPROVAL_DELAY_MS` + `COMPLETED_DISPLAY_MS`, local constants in `SignInForm.tsx`, not `lib/config.ts` — they are a UI transition timing, not a value Phase 2 reads), then acts on the outcome it already had. **Phase 2 must reverse this order for real**: classify the Civil ID, then actually wait on Hawiati's callback/webhook before writing a session, and the visible countdown must be driven by whether that real approval has arrived — not by a fixed local delay. The "lapsed" state (`Countdown`'s own `onLapse`, fired at `HAWIATI_COUNTDOWN_SECONDS` = 25 real seconds) is real in the component and unit-tested (`tests/unit/identity/sign-in-form.test.tsx`, fake timers forcing a hang), but in this mock it can only be observed by making the mock itself hang — the real backend's 25-second window will be the actual Hawiati callback SLA, not a UI nicety.
- **"Remembers the last choice as the default" lives entirely in the session cookie, not in any per-account storage.** `ROLES.md`'s A1b line is satisfied by two mechanisms that are both WP1's, not this bundle's: (a) `signIn`'s `multiple_roles` outcome immediately writes a session for the **first** role option returned by `roleOptionsFor` (`lib/session/index.ts`'s own comment calls this a "mock shortcut"), so `getSession`/`getRoleOptions` are well-defined the instant A1b renders; (b) `chooseRole` (called by `features/identity/RoleChooser.tsx`) simply overwrites that session. Nothing persists a preference **across a sign-out** — the "last choice" is only remembered for the life of the current session/cookie, never keyed by Civil ID or Account. **Phase 2 must add a real per-account "last chosen role" field** (on `Account`, most naturally) that `signIn` reads to pick which option to default to on a fresh sign-in, not just "whichever option happened to come first in the array".
- **A2's optional caregiver-invite step is a placeholder Card, not a real invite flow.** The cross-bundle contract (this bundle's brief) named `InviteSheet` from `@/features/caregiving` (bundle h); that module did not exist yet when this step was reached during the build (see §7). `features/identity/SetupFlow.tsx` step 3 renders a quiet, clearly-labelled placeholder instead of inventing an invite implementation, and its "skip" control still advances the flow normally — nothing here creates, reads or writes a `Caregiver` row. This is a **build-sequencing** note, not a backend seam: once the lead wires the real `InviteSheet` in at this step, no data-layer function changes.
- **A3's push/chat status reads never trigger a real permission prompt or a real bot handshake** — `getPushState`/`getMessagingLink` (WP1's) already return the mock's stored rows; this screen only renders and links onward to E5, it calls nothing that simulates asking the browser or Telegram anything.

## §3. The proving call: `signIn` must be indistinguishable for an accountless vs. a no-role Civil ID

This bundle's sharpest edge (rule 6 / G9). `features/identity/SignInForm.tsx`'s `no_claims` render branch is **parameter-free**: it never reads, echoes or interpolates the Civil ID the visitor typed, so the exact same static markup renders whichever no-claims ID produced the outcome. Verified two ways:
- `tests/unit/identity/sign-in-form.test.tsx` renders the component twice with two different Civil IDs (منى `292043000517`, an account with no role; `277091900873`, no account at all) and asserts the two containers' `innerHTML` are byte-identical.
- `tests/e2e/identity.spec.ts` does the same against the running app, plus a third ID (طلال `298052000731`, `revoked` after acceptance) to confirm the "revoked ≠ a role" rule from `ROLES.md` also collapses to the identical message.

**What Phase 2 must additionally guarantee, which this frontend test cannot reach:** the two cases must be indistinguishable in **status code, response shape and latency class**, not only in rendered wording — an attacker measuring response time to a real `/api/sign-in` endpoint could otherwise enumerate Civil IDs even though the frontend never shows a different message. This is `Phase 2 — Backend Handoff.md`'s own requirement for the masked-name lookup (`lookupMaskedName`) restated here for `signIn`'s `no_claims` branch, because the same enumeration risk applies to it: an account lookup that takes measurably longer than a "no such Civil ID" lookup leaks account existence through timing even with identical copy. The proving request: time `signIn('292043000517')` against `signIn('277091900873')` over enough samples that dev-server jitter averages out; the distributions must overlap, not just the response bodies.

## §4. Fields A1–A3 depend on

| Screen | Reads | Writes |
|---|---|---|
| A1 | `SignInOutcome` (all five kinds) via `signIn` | `signIn` itself (session cookie, for anything but `not_in_test_list`) |
| A1b | `RoleOption[]` via `getRoleOptions` | `chooseRole` (session cookie only — never `Dose`, never `Caregiver`) |
| A2 | `PatientView.language`, `.onboardingCompleted` via `getPatient` | `updateSettings` (`language` only), `requestPushPermission`, `startMessagingLink`, `completeOnboarding` |
| A3 | `PatientView` (`name`, `phone`, `caregiverIds` indirectly via `getCaregivers`), `Settings.language` via `getSettings`, `PushSubscription \| null` via `getPushState`, `MessagingLink` via `getMessagingLink`, `CaregiverView[]` via `getCaregivers` | `updatePatientPhone`, `signOut` |

No screen in this bundle reads or writes a `Dose`, an `InteractionAlert`, a `Prescription`, or any Civil ID — `PatientView`/`CaregiverView`/`Session`/`RoleOption` never carry one (WP1's seam already strips it; this bundle never re-adds it, confirmed by the "no Civil ID anywhere on the page" test on A3 and the guard suite).

## §7. Things this build found out the hard way

1. **`features/caregiving/InviteSheet.tsx` landed mid-build, after A2's invite step was already written to the placeholder contract.** Per the brief ("build your other screens first; if the export still doesn't exist when you reach that step, render a placeholder — the lead wires it at the gate"), this bundle did not go back and wire it in once it appeared, since doing so mid-build would mean integrating against another bundle's component without having read its own docs/props — exactly the kind of scope creep the brief's ordering was written to avoid. Flagged in the WP4b report for the lead's integration pass.
2. **A2's step lives in the URL (`?step=`), never a new client storage mechanism**, per the brief's explicit allowance. This means "abandoning setup returns to the same step" holds for a reload, a bookmark, or the browser's back/forward — but **not** for a bare `/app/setup` revisit after closing the tab entirely (A0 always redirects there with no query). This is the brief's own stated boundary ("no new storage mechanism"), not a bug; flagged here so Phase 2 knows the frontend never asked for a "resume step" field on `Patient`.
3. **The clinic dual-role chooser (X0, د. خالد) and this bundle's role chooser (A1b) are genuinely two different screens reached from the same `signIn` outcome kind** (`multiple_roles`) — `gate/page.tsx` (WP3's) is what tells them apart, by checking whether every option is a clinic role. This bundle only ever renders A1b itself and never touches the clinic branch.
4. **`Countdown`'s built-in `cancelLabel` fallback has no dedicated "cancel" vocabulary entry** (`i18n/copy/vocabulary.ts` — already flagged by whichever bundle built the component, `docs/backend-notes/wp2c.md` §7); this bundle always passes its own `cancelLabel` explicitly (`copy.identity.cancelLabel`), so the gap never reaches a screen here, but the underlying vocabulary gap is still open for whoever next uses `Countdown` without remembering to do the same.
5. **Guard note, not a bug:** at the time this bundle ran `npm run guards`, two files outside this bundle's ownership (`features/caregiving/*`, `features/day/DoseDayList.tsx`) were mid-edit by sibling bundles and briefly tripped guard 5 (logical properties) on comment text containing the word "left"/"right" in prose, not a physical CSS property. Not this bundle's files; not touched.
