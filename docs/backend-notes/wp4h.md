# WP4 bundle h — Invitation + caregivers (F0–F5): notes

## §2. Where the mock cheated

- **The masked-name lookup is computed against an in-process directory, not a rate-limited service call.** `lookupMaskedName` (`lib/data/mock/accounts.ts`, not this bundle's file — read-only) resolves a Civil ID against the seed's `Account` rows synchronously, with no request throttling. **The backend must rate-limit this endpoint per session and audit every call** (`Acceptance Criteria and Test Plan.md`, Phase 2 §"Masked-name lookup") — it is the one endpoint that could be abused to enumerate Civil IDs, and Phase 1 has no rate limiter anywhere.
- **Invitation expiry is a string comparison against `REFERENCE_NOW`, not a clock.** `pendingInvitationsFor` (`lib/data/mock/caregivers.ts`) filters `expiresAt > nowIso` at read time; there is no scheduled job that flips a stale `pending` row to `expired` — the seed's `cg-05` is simply seeded already-`expired`. **The backend needs both**: expiry enforced at read time (so a stale row is never offered for acceptance even one request before a job runs) **and** a job that actually transitions the row, so F1's list and the audit log read a real status rather than a live recomputation forever.
- **The invite-sheet's Civil ID field has no format check beyond twelve digits client-side** (`features/caregiving/InviteSheet.tsx`'s `CIVIL_ID_PATTERN`). The real Hawiati/Civil ID format validation belongs server-side; Phase 1 never claims to validate it beyond shape.
- **`InviteSheet`'s "created" outcome has no per-invitation identifier of its own to poll or confirm against** — it is a static panel, not a submission receipt. Phase 2's real invitation-creation endpoint should still return an id (never displayed, G9) so the client can distinguish "created" from a transient network failure, which this mock cannot fail in a way worth simulating.

## §4. Fields F0–F5 depend on

- **F0** renders nothing sensible without `InvitationSummary.patientFirstName` and `.relationship` (the whole "who is asking, and what they claim" sentence); `.status` and `.expiresAt` decide which of the four outcome panels renders. All five are effectively required for this screen — there is no partial-data state designed for it.
- **F1** depends on `Caregiver.name` (the patient's own claim, never a lookup), `.relationship`, `.status`, `.invitedAt`/`.expiresAt`/`.acceptedAt`/`.revokedAt` for the neutral-state wording (`relationshipStateLabel`, `features/caregiving/format.ts`). `lookupMaskedName`'s `maskedName` is optional by design (`null` is the no-account case, not a missing-data bug).
- **F2** depends on `Settings.adherenceCheckInEnabled` (gates every status pill and the tracking-off notice) and each `Dose.tracked` (gates the individual pill — the two are checked independently, deliberately, per `features/day/DoseDayList.tsx`'s own doc comment). Without `Prescription.drug.strengthMg`/`.strengthUnit` a card simply shows no strength line (`DetailRow`/`PrescriptionCard`'s own empty-value handling) — never "undefined".
- **F3**'s prescription detail is the one screen in this bundle that genuinely tolerates a mostly-empty record (`rx-006`-shaped rows, CR-002): every field is optional in the UI by construction (`DetailRow`'s em-dash). Its alert detail depends on `InteractionAlert.description` (the "what the risk is" sentence) and `.reviewStatus`; `.sourceCitation` is rendered verbatim even when it is the `TO_BE_SUPPLIED` placeholder (CR-014).
- **F4** depends on `CaregiverLinkView.patientFirstName`/`.acceptedAt` for its one identity line. **Gap, not patched here:** no published data function returns a caregiver's own display name (see §7 item 1) — this bundle renders an identity-verified line instead of a name row, which is a reduced but honest rendering, not a broken one.
- **F5** depends on nothing — static copy only, as `docs/SCREENS.md` specifies (no data function listed for F5).

## §7. Things this work found out the hard way

1. **No published data function returns a caregiver's own display name.** SCREENS.md's F4 row lists `getCaregiverLink, getPushCapability, getPushState, requestPushPermission, disablePush, getMessagingLink, startMessagingLink, disconnectMessaging, selfUnlink, signOut` as F4's data functions — none of them carries the caregiver's own name, and `CaregiverLinkView` (the only shape `getCaregiverLink` returns) has exactly `{patientId, patientFirstName, acceptedAt}`. F4's own prose ("own name") cannot be satisfied by the frozen interface as published. Per the working agreement ("a missing function is a request to the lead, never invented inline"), this bundle did **not** add a function or contract field; `features/caregiving/CaregiverProfile.tsx` renders an identity-verified line (CR-026's A3 pattern: "verified through the simulated Hawiati flow") in its place. Needed change: either a `getCaregiverLink` return-shape addition (`ownName`, Civil-ID-stripped) or a documented decision that F4 never shows a name at all.
2. **`PrescriptionCard` takes `onOpen: MouseEventHandler`, not `href`** (already logged by bundle c, `docs/backend-notes/wp4c.md` §7, and reused here via `features/day/MedicinesList`'s `PrescriptionCardLink` wrapper) — F2's Medicines screen therefore renders its per-prescription navigation as `<button>`s calling `router.push`, not real `<a>` elements. Functionally identical for a screen reader and for "tap opens detail", but it means "zero write controls" tests must enumerate these as the allowed navigation shape rather than assert literally zero `<button>` elements (`tests/unit/caregiving/zeroWriteControls.test.tsx`, `tests/e2e/caregiving.spec.ts`).
3. **`features/day` (bundle c) landed mid-build.** F2's Today/Medicines screens were first written composing `ScheduleGroup`/`DoseRow`/`PrescriptionCard` directly (the DEPENDENCIES §1 fallback, since `features/day` did not exist yet when this bundle started); once `DoseDayList`/`MedicinesList` landed they were swapped in with `readOnly` and a `hrefBuilder` into this bundle's own `/care/...` routes, per the brief's primary instruction. No lasting duplication remains — `features/caregiving/format.ts` now only holds the F3-specific helpers `features/day` has no equivalent for (strength/unit formatting, dosing-pattern/status labels, dose-timeline "when" formatting, F1's relationship-state label, F3's activity-href mapping).
4. **The shared dev-server store is a real hazard for e2e tests that mutate a `Caregiver` row.** D-002's mock store is a module-level singleton that survives for the life of the process, and several other bundles' e2e suites (`roles.spec.ts`, `identity.spec.ts`) read routing behaviour for ناصر's pending invitation (cg-03) — harmlessly, since they only assert on the URL a redirect lands on, never on the invitation's content or status. `tests/e2e/caregiving.spec.ts` performs exactly two real state transitions (`cg-03` pending → active via a real accept click, `cg-08`/سارة's incoming pending invitation → declined via a real decline click) and both are written idempotently (each checks the invitation's current state before clicking), so a re-run or a stray parallel worker observes the post-condition instead of erroring. **Flagged for the lead:** if a later gate runs the full e2e suite together, `cg-03`'s status will read `active` and `cg-08`'s `declined` from that point on for the rest of that server process's life — this is expected from exercising F0's own actions, not a bug, but any sibling bundle that assumes ناصر/سارة's invitations stay `pending` for a *content* assertion (not just a routing one) should run before this bundle's e2e suite, or the dev server should restart between bundles' e2e runs.
5. **`tests/e2e/caregiving.spec.ts` hit `net::ERR_CONNECTION_REFUSED` mid-run twice** against the shared dev server on port 3100 (consistent with the brief's own warning about port/infrastructure contention from sibling agents). Both times a retry after the server came back up succeeded; no code change was needed. Logged here rather than in a code comment because it is an execution-environment fact, not a product one.
6. **The Next.js dev-mode indicator is a real `<button>` in an open shadow root, and Playwright locators pierce it.** A bare `page.locator('button')` on any screen under `next dev` (never a production build) picks up this one extra element. Every "zero/enumerated buttons" assertion in `tests/e2e/caregiving.spec.ts` is scoped to `#main-content` (every shell wraps its screen's content in that id) to exclude it.
