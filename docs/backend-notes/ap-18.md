# AP-18 · Robustness

**Why.** `docs/AGENTS-POLISH-PLAN.md` § 7.3: an error workflow that tells the team when any Jur'ah
workflow fails; `Settings.notificationChannel` actually respected by alert delivery; the Alexa request
signature investigated; the web assistant's loading state proven against the real 4-11 s latency. All
four steps are code-only here — every live step (importing/publishing `agent-error`, setting
`settings.errorWorkflow`, the owner's CR-104/CR-105 calls, a pre-merge production read) is owed to the
lead, listed at the end.

## What changed

| File | Change |
|---|---|
| `agents/lib/error-alert.js` (new) | `errorAlertText(payload, nowIso)`: the plain-ASCII message an error workflow's Code node sends to the team. Reads only `workflow.name`, `execution.lastNodeExecuted`, `execution.url` and the passed-in Kuwait time — never `execution.error` (`.message`/`.description`/`.stack`), because that is the failed run's OWN data and can carry a patient's name, Civil ID, chat id or link token. Every field is trimmed and length-capped; a missing or malformed payload falls back to `(not given)` instead of throwing. |
| `agents/scripts/build-error-workflow.js` (new) | A generator separate from `agents/scripts/build.js` (that file is being edited by another lane) that writes `agents/workflows/agent-error.json`: an Error Trigger, a Code node ("message (deterministic)") that inlines `error-alert.js` and computes the Kuwait time from n8n's own `$now` (every Jur'ah workflow's `settings.timezone` is `Asia/Kuwait`, so `$now.toISO()` is already Kuwait-local — no locale library), and a Telegram send whose `chatId` is the owed `TEAM_CHAT_ID` constant (`'[TO BE SUPPLIED]'`), plain text, no credentials block. `settings.errorWorkflow` is never set on this workflow itself, so a failed send here cannot re-trigger itself. Exports `buildWorkflow`, `serialise` and `TEAM_CHAT_ID` (module-scope, not local) so `check-error-workflow.js` reads the same constant back rather than holding its own copy of the exact text. |
| `agents/scripts/check-error-workflow.js` (new) | `checkErrorWorkflow(wf)`: exactly the three node types in order; wired Error Trigger → Code → Telegram, nothing else; `chatId` is exactly `build-error-workflow.js`'s `TEAM_CHAT_ID` (never a real value or an expression); no committed credential; the Code node compiles as n8n compiles one, and its source can never reference `.error.message`/`.error.stack`/`.error.description` or `execution.error` directly; never set as its own error workflow. `checkCommittedFile(file?)`: the file is ASCII and byte-identical to a fresh in-memory build (no shelling out) — a hand-edit after the last rebuild goes red; a missing file goes red on Node's own `ENOENT`, never special-cased. Runs standalone (`node scripts/check-error-workflow.js`, exit 1 on the first failure) and is exported for tests. |
| `agents/workflows/agent-error.json` (new, generated) | The committed output of `build-error-workflow.js`: 3 nodes, ASCII-only, round-trips. |
| `agents/test/error-workflow.test.js` (new) | `errorAlertText`: names the workflow/node/time/URL; a poisoned payload (a fake Civil ID, chat id and two token-shaped strings inside `error.message`/`.description`/`.stack`) never surfaces any of them; ASCII-only, no em dash; a malformed payload never throws; an overlong field is capped, not truncating the shape. A runtime proof (not only the static compile check): the GENERATED Code node's actual source, executed through `new AsyncFunction('$input', '$now', jsCode)` with both stubbed, builds the real message and still drops the poisoned data. `checkErrorWorkflow`/`checkCommittedFile`: green on the committed file; red on a numeric `chatId`, a Code node edited to read `error.message`, a fourth node, a committed credential, this workflow set as its own error workflow, and a missing file. |
| `agents/scripts/drift.js` | `NORMALISE_SOURCE` (the shared node-hashing function, used both here and pasted into the n8n browser console) now also masks a **literal** (non-expression) `chatId` before hashing — the same live-only-config treatment already given the Alexa skill id and device links. Every OTHER workflow's Telegram nodes address `chatId` with an `={{ ... }}` expression, so this can never hide drift there; only a hard-coded value (today, only `agent-error`'s) is masked. |
| `agents/test/drift.test.js` | One new case: a live copy of `agent-error` with a real chat id (`build-error-workflow.js`'s `TEAM_CHAT_ID`, read back rather than retyped) hashes equal to the committed file — no drift; a further edit to the SAME Telegram node, or to the Code node, still reads as drift, naming the node. A second new case proves the masking rule itself is specific to a literal value: two different `={{ ... }}` expressions still hash differently; two different literals hash the same (masked). |
| `agents/package.json` | `build` and `check` now chain the new scripts after the existing ones (`node scripts/build.js && node scripts/build-error-workflow.js`; `node scripts/check.js && node scripts/check-error-workflow.js`). `agents/scripts/build.js` and `check.js` themselves are untouched. |
| `agents/README.md` | One added sentence in the known-demo-limits paragraph, pointing at CR-104 and this file. |
| `lib/data/pg/agent.ts` | `recipients` SQL gains one more correlated subquery: `(select st.notification_channel::text from settings st where st.patient_id = $1) as notification_channel` (the same shape as the existing `language` subquery beside it — `jurah_agent` already holds `select` on `settings`, migration 0005). `Recipients` gains `notificationChannel: Settings['notificationChannel']`; `recipientsFor` normalises the raw column value (`null`, or anything the four-value enum does not hold) to `'none'` — never guessed at by the caller. |
| `lib/agent/notify.ts` | `deliverAlert`'s Telegram send for a `patient` target now also requires `recipients.notificationChannel === 'telegram'`; a caregiver target is unaffected (no `Settings` row exists for one), and push is unaffected either way (governed by the granted subscription alone, `contracts.ts:224`). Header comment updated to state the rule and its two exceptions. |
| `tests/unit/agent/notify.test.ts` (new) | Six cases, described below. |
| `tests/unit/assistant/AssistantLauncher.test.tsx` | One new parametrised test (4 000 ms and 11 000 ms), described below. No screen file changed — the existing code already holds the wait state for the whole delay, so no Hallmark audit or UX checklist applies (nothing on screen was touched). |
| `docs/DECISIONS.md` | CR-104 (Alexa signature, `PROPOSED`) and CR-105 (`notificationChannel`'s built reading, plus the open question of how a patient ever gets `'telegram'`, `PROPOSED`) appended at the end. |

Not changed: `agents/scripts/build.js`, `agents/scripts/check.js` (another lane owns the first; the
second needed no edit — it does not enumerate the workflows directory, so it never had to learn about

**7. The Alexa request signature — read-only research, no live system touched.** Amazon's own
certification requirement (`https://developer.amazon.com/en-US/docs/alexa/custom-skills/host-a-custom-skill-as-a-web-service.html`,
read 2026-09-24): "Web services that accept unsigned or out-of-date requests will not pass
certification." n8n's own docs (`https://docs.n8n.io/build/code-in-n8n/using-the-code-node`, read
2026-09-24): "If you use n8n Cloud, you can't import external npm modules. n8n makes two modules
available for you: crypto Node.js module, moment npm package" — answering, from n8n's own
documentation rather than guesswork, whether the Cloud Code node can `require('crypto')` at all: yes.
The same page, under "File system and HTTP requests": "You can't access the file system or make HTTP
requests" from a Code node — so the certificate chain must be fetched by an HTTP Request node, not the
Code node itself, matching CR-104's Option A shape below. The Webhook node's documented "Raw Body"
option (`https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.webhook`, read 2026-09-24)
is the node's own way to receive the exact bytes a signature is computed over.
