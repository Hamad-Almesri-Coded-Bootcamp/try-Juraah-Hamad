# AP-08 · Evaluation harness

## Why

Every agents test stubs the model, so none of the spec's data-based pass criteria has ever been
measured (`docs/AGENTS-POLISH-PLAN.md` 7.3, AP-08). This package builds the harness that measures
them. The numbers themselves are AP-15, once people supply the sets.

## What changed

**`agents/eval/`** (new).

- `datasets/`: one schema file and one **empty** data file per set of plan section 9
  (`extraction`, `adherence`, `screening-interacting`, `screening-non-interacting`, `travel`,
  `routing`), and `datasets/README.md` saying who supplies each set and its minimum. Each empty data
  file carries an `owed` line with the owed-value marker, so the gate count finds all six (the count
  in `agents` and `lib` goes from 15 to 21).
- `thresholds.js`: the one constant holding every threshold and minimum, copied from
  `docs/AI Agents Acceptance Criteria.md`.
- `run.js`: the runner. `datasets.js` (load, validate, minimum), `schema.js` (a JSON Schema
  validator for the subset the schemas use; an unknown keyword is an error), `workflow.js` (runs a
  committed workflow's own Code nodes, reads a chain node's prompt, schema and models),
  `gemini.js` (the model call; `GEMINI_API_KEY` from the shell, in a header, never printed),
  `sets.js` (one adapter per set).
- `README.md`: how to run it, what each set is scored on, the one transport difference.

**How "exact" is kept.** The harness does not re-implement an agent. For extraction and travel it
runs the committed workflow's own `input (deterministic)` node to build the vision request, sends
that body to the URL of the workflow's own Gemini node, and runs the workflow's own `validate` or
`check` node on the answer. For screening it runs the DDInter workflow's own `input` and `screen`
nodes. For adherence it reads the prompt, schema and models from the committed
`Gemini: classify the reply` node, refuses to run if they differ from `agents/lib/adherence.js`,
and applies `trustClassification` (G11).

**"One string".** The three model prompts and schemas that lived inside `agents/scripts/build.js`
moved into the lib module that owns each one's logic, exported:

| Prompt and schema | Now in | Beside |
|---|---|---|
| adherence classification (`CLASSIFY_PROMPT`, `CLASSIFY_SCHEMA`) | `agents/lib/adherence.js` | `INTENTS`, `trustClassification` |
| web chat (`WEBCHAT_PROMPT`, `WEBCHAT_SCHEMA`) | `agents/lib/webchat.js` | `WEBCHAT_INTENTS`, `trustWebchatIntent` |
| voice free talk (`FREE_TALK_PROMPT`, `FREE_TALK_SCHEMA`) | `agents/lib/voice-actions.js` | `FREE_INTENTS`, `trustFreeTalk` |

Each sits in a "model contract" block at the end of its file. `build.js` changed in four places
only: the three string sites now `require` the exports, and `inline()` cuts the model-contract
block, so no Code node's source changes. The rebuilt workflows are byte-identical to `origin/main`
(proof below), and a test asserts that each chain node carries its lib module's exact prompt and
schema and that each schema offers exactly the intents its trust rule accepts.

**Change request.** CR-099 (`PROPOSED`, for Hamad) records how the harness reads what the spec
leaves open: which twelve fields are "core", what "identification" and "recall" count, that the
non-interacting set is reported with no invented threshold, what "representative" means, the
routing labels, and the one transport difference.

## For whoever merges the Telegram lane

AP-02 (voice) and AP-05 (adherence) may edit the prompt text that used to sit in `build.js`. After
this merges, that text lives in `agents/lib/voice-actions.js` (`FREE_TALK_PROMPT`,
`FREE_TALK_SCHEMA`) and `agents/lib/adherence.js` (`CLASSIFY_PROMPT`, `CLASSIFY_SCHEMA`): a merge
conflict at the old `build.js` lines is resolved by keeping the `require` line and applying the
edit to the lib module. `agents/test/eval-contracts.test.js` fails if the rebuilt workflow and the
lib module disagree.

## Live steps for the lead after merge

None. The workflows are byte-identical to `origin/main`, so nothing is published, and no database,
n8n, Vercel or Alexa setting changes. The drift report after merge is the same as before it.
