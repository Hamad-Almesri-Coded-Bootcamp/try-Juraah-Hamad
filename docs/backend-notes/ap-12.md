# AP-12 · The audit insert policy (CR-061)

Branch `polish/ap-12-audit-insert-policy`, from `origin/main` at `d5cd026`. Change request: `docs/DECISIONS.md` CR-091 (`PROPOSED`: the migration still has to be applied to production, which merging does not do).

## What the finding was

0005 gives `audit_events` two insert policies: `audit_insert_session` for `jurah_app` (`with check (jurah_session() is not null)`) and `audit_agent_insert` for `jurah_agent` (`with check (true)`). So any `jurah_app` session can write a row naming any actor. CR-061: a patient session could write `actor_role = 'agent'`. Reading the policies and the trigger for this package found a second hole of the same kind: `audit_dose_status_actor` admits `'system'`, so any `jurah_app` session, the system session included, could also write a `dose_status_recorded` row naming `system`. Either row forges the proof that no dose status came from the interface. Only `append()` writes rows today (guard 8), so no product path does it; the database did not refuse it.

No `jurah_app` session ever fires the trigger. It runs `after update of status on doses` (0004), and `jurah_app` holds `update (scheduled_at, tracked)` on `doses` only (0005:119); the status grant is `jurah_agent`'s alone (0005:121). The one `update doses set status` in `lib/` is `lib/data/pg/agent.ts:42`, under `withAgent()`. So 0014 refuses `dose_status_recorded` from every `jurah_app` session, the system session included: a system session writing it could only be a forgery, because `jurah.session` is a setting any caller can set. The static test asserts the grants and the trigger, so a change to either fails `npm test` before it meets 0014.

The `recomputeSchedule` D-025 row is why a policy that takes the agent actor from `jurah_agent` alone would break production: the discontinuation the agent asks for runs as the system actor (D-025) and names the agent, and `tests/integration/enforcement/agent.test.ts` asserts that.

## The SQL

```sql
drop policy if exists audit_insert_actor on audit_events;
create policy audit_insert_actor on audit_events as restrictive for insert to jurah_app with check (
  jurah_session() is not null
  and type <> 'dose_status_recorded'
  and (actor_role <> 'agent' or (jurah_session_is('system') and type = 'prescription_discontinued'))
);
```

(The file also carries the header comment that explains each clause. md5 of the committed LF text: `822ec56a6d5f0de118fa77a893a9b12f`.)

The rule, as a table (`jurah_app` only; `jurah_agent` keeps 0005's `audit_agent_insert`):

| Session | Row naming `agent` | `dose_status_recorded` row | Anything else |
|---|---|---|---|
| none | refused (0005 already) | refused | refused (0005 already) |
| `system` (`withSystem()`) | only `prescription_discontinued` (D-025) | **refused** (no `jurah_app` writer produces it: `jurah_app` cannot update `doses.status`, 0005:119) | admitted |
| patient, caregiver, reviewer, admin, pending-only | **refused** | **refused** | admitted, as before |

Why restrictive: Postgres ANDs a restrictive policy with the permissive ones, so `audit_insert_session` still requires a session, and a re-apply of 0005 (which drops and recreates its own policies by name) cannot undo 0014. A restrictive policy's name is in its error message, so every refusal test names `audit_insert_actor`.

Why `system` cannot be claimed by a user: `withSession()` builds the session payload from the verified cookie, and `lib/session/verify.ts` admits only `patient`, `caregiver`, `reviewer`, `admin` (the static test asserts that line); the cookie is signed (D-018). That closes the product path, not raw SQL: `jurah.session` is a setting any caller can set, so a caller running SQL as `jurah_app` can claim `{"role":"system"}`. What such a caller can still write after 0014 is the D-025 row, `prescription_discontinued` naming the agent. It can no longer write any `dose_status_recorded` row, which is the rule-1 proof. Closing the D-025 residue needs D-025's row to name the system actor or come from `jurah_agent`, which changes `tests/integration/enforcement/agent.test.ts`; it is listed as open in CR-091.
