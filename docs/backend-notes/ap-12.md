# AP-12 · The audit insert policy (CR-061)

Branch `polish/ap-12-audit-insert-policy`, from `origin/main` at `d5cd026`. Change request: `docs/DECISIONS.md` CR-091 (`PROPOSED`: the migration still has to be applied to production, which merging does not do).

## What the finding was

0005 gives `audit_events` two insert policies: `audit_insert_session` for `jurah_app` (`with check (jurah_session() is not null)`) and `audit_agent_insert` for `jurah_agent` (`with check (true)`). So any `jurah_app` session can write a row naming any actor. CR-061: a patient session could write `actor_role = 'agent'`. Reading the policies and the trigger for this package found a second hole of the same kind: `audit_dose_status_actor` admits `'system'`, so a patient session could also write a `dose_status_recorded` row naming `system`. Either row forges the proof that no dose status came from the interface. Only `append()` writes rows today (guard 8), so no product path does it; the database did not refuse it.

## The SQL

```sql
drop policy if exists audit_insert_actor on audit_events;
create policy audit_insert_actor on audit_events as restrictive for insert to jurah_app with check (
  jurah_session() is not null
  and case
        when jurah_session_is('system') then actor_role <> 'agent' or type = 'prescription_discontinued'
        else actor_role <> 'agent' and type <> 'dose_status_recorded'
      end
);
```

(The file also carries the header comment that explains each clause. md5 of the committed LF text: `71009e74bf6d07c88bc63d3c233ee023`.)

The rule, as a table (`jurah_app` only; `jurah_agent` keeps 0005's `audit_agent_insert`):

| Session | Row naming `agent` | `dose_status_recorded` row | Anything else |
|---|---|---|---|
| none | refused (0005 already) | refused | refused (0005 already) |
| `system` (`withSystem()`) | only `prescription_discontinued` (D-025) | admitted (actor `system`; the CHECK refuses user actors) | admitted |
| patient, caregiver, reviewer, admin, pending-only | **refused** | **refused** | admitted, as before |

Why restrictive: Postgres ANDs a restrictive policy with the permissive ones, so `audit_insert_session` still requires a session, and a re-apply of 0005 (which drops and recreates its own policies by name) cannot undo 0014. A restrictive policy's name is in its error message, so every refusal test names `audit_insert_actor`.

Why `system` cannot be claimed by a user: `withSession()` builds the session payload from the verified cookie, and `lib/session/verify.ts` admits only `patient`, `caregiver`, `reviewer`, `admin` (the static test asserts that line); the cookie is signed (D-018).
