# WP4 bundle f — Drug check + refill (C3, D1): notes

## §2. Where the mock cheated

- **`checkDrugPhoto`'s outcome is a coin-flip on the patient's own store, not a vision model.** `lib/data/index.ts`'s `checkDrugPhoto` (not this bundle's file — read-only) identifies "the drug" as the patient's own **first active prescription in store order** (`store.prescriptions.find(p => p.patientId === patientId && p.status === 'active')`), then checks whether that prescription is one side of the patient's own `danger`-severity `InteractionAlert`. A 0-byte image is the one deliberate escape hatch to `could_not_identify` (the fixture switch this bundle's tests use — `tests/e2e/supply.spec.ts`, `tests/unit/supply/DrugCheckFlow.test.tsx`). The real pipeline this must become: an actual image-recognition step that identifies the photographed packet (brand/generic name, strength) independent of which prescriptions the patient happens to have on file, followed by the **same** interaction screening this contract already promises ("screened against the patient's full active profile") — the screening step's shape (name in, verdict + optional alert id out) is worth keeping; only the identification step is the part that is currently faked.
- **The routing rule (`routedTo`) is computed once, in `getRefillOverview`, and never re-derived by this bundle.** `RefillLine.routedTo` and `RefillRequest.routedTo` are both `rx.source.sector === 'public' ? 'public_pharmacy' : 'private_pharmacy'`, computed server-side in `lib/data/index.ts`. `features/supply/RefillList.tsx` and `features/supply/format.ts` only read this field and translate it to a catalogue word (`destinationLabel`) — nothing here recomputes it from `source.sector`, so a future backend only needs to keep computing it the same way at the same seam boundary (`getRefillOverview`/`requestRefill`), never trust a client-supplied value for it (see §3).

## §3. Rules that are currently absences, and must become refusals

|---|---|---|---|

## §4. Fields C3/D1 depend on, and what renders instead when they are absent

- **C3** (`features/supply/DrugCheckFlow.tsx`) needs only `DrugCheckOutcome` itself: `kind: 'could_not_identify'` renders the explicit `ErrorState` and nothing else; `kind: 'identified'` needs `drugName` (always present) and `verdict`, plus `alertId` only when `verdict === 'interaction_found'` — the mock's own invariant is that `alertId` is set exactly when `verdict` is `'interaction_found'` (`lib/data/index.ts`'s own ternary), so this bundle renders the `InteractionAlert` summary and its "open interaction details" button only when both are present together; a hypothetical `interaction_found` with no `alertId` would silently render no hand-off button at all rather than crash (worth a contract note if the backend could ever produce that combination, which the current mock cannot).
- **D1** (`features/supply/RefillList.tsx`) needs `RefillLine.daysRemaining !== null` (alongside `remaining`/`total`, which are `null` in the exact same cases per `lib/schedule/depletion.ts`) to decide whether to render `DepletionMeter` at all — never a fabricated estimate. `RefillLine.brandName` is optional and simply omitted from the card's heading when absent (`rx-005`-shaped generic-only records, per `docs/Seed Dataset.md`). A `RefillRequest` whose `prescriptionId` no longer resolves to a line in the current `getRefillOverview` result (e.g. the prescription was discontinued after the request was made) renders in "My requests" with the catalogue's own neutral fallback label (`copy.supply.d1UnknownPrescriptionLabel`) rather than "undefined" or the raw id — unreachable against the current seed (every seeded `RefillRequest` points at a still-active prescription) but exercised defensively.

## §7. Things this work found out the hard way

1. **`getRefillOverview` does not filter out a `needsReview`/`fieldReviewStatus: "pending"|"returned"` prescription.** Its only filter is `status === 'active'` (`lib/data/index.ts`, not touched here); فاطمة's `rx-006` (`drug.genericName: '(unreadable)'`, `needsReview: true`, `fieldReviewStatus: 'pending'`) and `rx-007` (`fieldReviewStatus: 'returned'`) both carry `status: 'active'` in the seed and would therefore appear as ordinary refill-able lines if her session were used for this screen. This bundle's own explicit test patient for the "no dispensing → no estimate" states is سارة (`rx-008`/`rx-009`, both field-clean) rather than فاطمة, specifically to avoid exercising this gap incidentally; nothing in `features/supply/**` filters `needsReview`/`fieldReviewStatus` out, because doing so in the UI layer alone (rather than at the seam, which this bundle does not own) would be exactly the kind of silent, undocumented data-shape decision CLAUDE.md's working agreement asks to be logged instead of made quietly. **Recommended follow-up for whoever owns `lib/data/index.ts`:** `getRefillOverview` should exclude a prescription whose fields are not yet confirmed (`needsReview` or `fieldReviewStatus` in `'pending'`/`'returned'`) — there is nothing coherent to say about "remaining supply" for a prescription whose dose or strength is itself still in question.
2. **"Already requested" is read as `RefillRequest.status === 'requested'` only — `'approved'` does not suppress a new request.** حمد's own seed carries two requests: `rf-01` (`rx-003`, `requested`, 2026-09-20) and `rf-02` (`rx-001`, `approved`, 2026-08-20 — *before* `rx-001`'s own dispensing on 2026-09-01, i.e. a resolved past cycle that the current dispensing already reflects). The brief's own acceptance line only names `rx-003` ("the already-requested seeded line … renders as requested from first load"), never `rx-001`, which is the reading this bundle took: only a live, unresolved `'requested'` row hides the button and shows the InlineNotice; `'approved'`/`'denied'` are past outcomes that leave the button offered again. This is a **reasonable reading of an underspecified rule**, not a silent contract change (the `RefillRequest.status` enum and `getRefillOverview`'s shape are both unchanged) — but SCREENS.md/the Acceptance doc never states the rule this precisely, so if the owner intended *any* existing request (regardless of status) to suppress a new one, that is a one-line change in `features/supply/format.ts`'s `pendingRequestFor` (filter on presence rather than `status === 'requested'`), not a data-layer change.
3. **`DepletionMeter`'s `unit` prop is left unset, matching `features/prescription/PrescriptionDetail.tsx`'s (bundle d, B3) own precedent.** Neither `Prescription` nor `RefillLine` carries a dose-form word ("tablet", "capsule", …) anywhere in the contract; the approved `Refill.dc.html` board hardcodes "حبة" (tablet), which is true of every one of حمد's own seeded prescriptions but is not a real field. Rather than invent a unit word not backed by any data, this bundle followed B3's own established choice and passed no `unit` at all — the meter shows bare counts ("20 / 60"), which is honest given what the contract actually carries.
4. **The Playwright run against the shared dev server intermittently threw a `browserContext.close: ENOENT … .zip`/`.trace` teardown error** on one otherwise-unrelated test, on one run out of several full `tests/e2e/supply.spec.ts --workers=1` passes — never the same assertion, never an `expect(...)` failure, always the trace-writer's own file handle (the same class of flake bundle e's own notes recorded for `tests/e2e/safety.spec.ts`). Re-running only that one test in isolation passed immediately; a clean `test-results` directory before the final run also produced a fully clean pass. Not a code defect.
5. **A guard against re-running the store-mutating D1 test more than once per full invocation needed a locale guard, not only a project guard.** This file's own describe blocks are generated once per locale (`for (const [locale, dir] of LOCALES) { … }`), so a mutating test guarded only with `test.skip(testInfo.project.name !== 'desktop-1440', …)` still ran twice on that one project — once per locale pass — against the same live store, and the second pass broke the first pass's own already-mutated assumptions as well as the *other* locale's still-pristine assertions declared earlier in the same file. The fix guards on **both** `project.name === 'desktop-1440'` and `locale === 'en'` (the locale processed last), so the mutating test runs exactly once, after every pristine-state assertion in the file has already executed. Recorded here since the brief's own "hard-won lesson" about per-project mutation guards did not mention the per-locale multiplication, and the next bundle to add a locale-looped, store-mutating e2e test will hit the same thing.
