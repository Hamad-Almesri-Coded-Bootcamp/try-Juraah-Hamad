# AP-17 · Language

Branch `polish/ap-17-language`, from `origin/main` at `c53ca22`. Change request: `docs/DECISIONS.md` CR-103 (`PROPOSED` - no production schema change and no human-owed value needed for what this package builds; the option it proposes for the open gap is a separate, later change).

## What the finding was

`docs/AGENTS-POLISH-PLAN.md` §7.3 AP-17, under D7/CR-079 ("Fusha in text the app shows; the Kuwaiti register stays in Telegram and on Alexa"): the app speaks Fusha, but `agents/lib/webchat.js` (the web-app assistant CR-067 relies on) still answered in Kuwaiti dialect for four intents (`next_dose`, `dose_amount`, `today`, `forgot`) by reusing `agents/lib/voice.js`'s spoken words verbatim, plus three em dashes and one stale navigation label (`«المزيد ← الإشعارات والمراسلة»`, the app's actual label is `«الإشعارات والرسائل»`). `agents/lib/screening.js:106` carried one more em dash in stored alert text the app shows on C2. Since CR-102 (`polish/voice-follow-page-only`, already merged into `main` before this branch was cut) the app no longer shows Alexa's own words in its assistant panel, so `agents/lib/voice.js` and `agents/lib/voice-actions.js` correctly keep their Kuwaiti register - they needed no wording change, only the same em-dash check (both already had zero, confirmed below).

The three em dashes are gone. `next_dose`/`dose_amount`/`today`/`forgot` no longer call `voiceReply` at all: new local helpers `chatTime` (written Fusha time, `"الساعة 7 صباحًا" … "الساعة 11:55 ليلًا"`, digit-colon minutes, day-part words that are never `"الصبح"`/`"بالليل"`) and `chatAmount` (same quantity/strength wording as `voice.js`'s `spokenAmount` - that part was never a dialect problem) replace `voice.js`'s `spokenTime`/`spokenAmount` for the chat, while replicating its exact dose-selection rules (next = first open dose after now; amount = the one due within an hour else next; forgot = every open dose at or before now, ALL of them prompted to Telegram, only the most recent one named in the reply). `forgot`'s reply no longer says "nothing was recorded by voice" - it was never voice; it says the buttons went to Telegram. `voice.js` and `voice-actions.js` are untouched (per the plan: no edit), so `agent-alexa.json`'s generator input did not change. `VOICE_FOR` (only ever used for its key set) is renamed `DOSE_INTENTS` and simplified to a plain array now that it no longer needs to name a voice intent. ## Why no payload-field change request, and what CR-103 proposes instead

The plan's step for AP-17 asks for a change request only if a screening request does not carry the patient's language. Checked directly (not assumed): every screening call this session could find in the codebase already carries it - `lib/data/pg/reads-rx.ts:295-307` (`selectLanguage` re-read, then `requestScreening`), the Telegram path (`lib/agent/inbound.ts` `subject.language` into `agents/scripts/build.js`'s `screeningBody`), and the knowledge-side extraction-save path (`agents/knowledge/scripts/build.js`'s own `screeningBody`). So CR-103 is not that field; it records a different, real gap this work surfaced: an alert's `description` is stored once, in the patient's language at screening time, and every OTHER reader (a caregiver, a reviewer, the same patient after switching locale) sees it in that same stored language, because `localizeText` (`i18n/localize.ts`) only translates five hardcoded seed sentences and `AsWritten` only marks foreign-script runs - it does not translate. CR-103 proposes two options (translate known `ALERT_TEXT` shapes at display, or store both languages - the second needing a migration) and builds neither; it is `PROPOSED` for the owner or the lead to decide.
