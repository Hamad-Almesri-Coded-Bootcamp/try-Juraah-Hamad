# WP4 bundle d — B3 (prescription detail) and B4 (add/scan prescription): notes

## §2. `submitPrescriptionImage`'s canned outcomes — what the real pipeline must return per outcome

`lib/data/index.ts`'s `submitPrescriptionImage` (unedited here — `lib/**` is out of this bundle's
file list) picks its outcome from the chosen image `Blob`'s **byte size** — 0 bytes → `unreadable`,
1–99 bytes → `needs_review`, 100+ bytes → `confident` — never a real vision/extraction call. This
bundle's `tests/e2e/prescription.spec.ts` and `tests/unit/prescription/AddPrescriptionFlow.test.tsx`
both reach every B4 state through this same byte-size switch, through the published API only
(`submitPrescriptionImage`/`savePrescriptionDraft`), exactly as the brief asks.

What Phase 2's real extraction pipeline must return, per outcome, for `AddPrescriptionFlow.tsx` to
keep working unmodified:

- **`confident`** — `{ kind: 'confident', draftId, prescription: Partial<Prescription> }` with every
  one of the five CR-002 fields present (`brandName` optional only for a genuine generic-only
  record) and `needsReview: false`. The mock's own confident branch is itself slightly short of this
  — its `Partial<Prescription>` has no `startDate` even though `needsReview` is `false` — see §7.1.
- **`needs_review`** — the same shape plus `uncertainFields: string[]`, naming exactly the contract
  field keys (`'strengthMg' | 'frequencyPerDay' | 'startDate' | 'doseTimes' | 'brandName' | ...`)
  the pipeline could not read with confidence. `AddPrescriptionFlow` marks only the fields named in
  this array with the "Unclear" empty mark — a field absent from the array but also absent from
  `prescription` still renders (correctly) with `DetailRow`'s own default "Not recorded" mark instead,
  which is the right behaviour for "the prescriber genuinely wrote nothing here" but the wrong one
  for "we could not read this specific field" if the real pipeline ever omits a field from both the
  object *and* `uncertainFields`. **The real pipeline must put every field it is not confident about
  into `uncertainFields`, even when it also has no value to offer for it** — otherwise the screen
  cannot tell "the prescriber left this blank" from "we could not read this."
- **`unreadable`** — `{ kind: 'unreadable' }` and nothing else. `AddPrescriptionFlow` never
  constructs a `Prescription` in this branch; the medicines list is provably unchanged
  (`tests/e2e/prescription.spec.ts`'s own assertion, and `tests/unit/prescription/
  AddPrescriptionFlow.test.tsx`'s `getPrescriptions` before/after count).

## §4. Fields B3/B4 are blank without (CR-002)

- **`brandName`, `strengthMg`, `frequencyPerDay`, `startDate`, `doseTimes`** — rx-006 (فاطمة, the
  seed's core-fields-only record) carries none of the five. B3 renders every one of them via
  `DetailRow`, which shows its own empty mark ("—" / "Not recorded") rather than "undefined" for
  each — the exact case `tests/unit/prescription/PrescriptionDetail.test.tsx` and
  `tests/e2e/prescription.spec.ts` assert against directly. **`doseTimes` is the one field F3
  (bundle h's read-only twin) never renders at all** — see the parity note below; B3 does render it,
  and rx-006 is the record that proves the empty-mark path holds for it too.
- **`dispensing`** — absent on rx-005 (فاطمة) and rx-009 (سارة). B3's dispensing block itself never
  disappears (`DetailRow.md`: "don't hide the block it sits in" — every row inside it shows its own
  empty mark), and the `DepletionMeter` is the one piece that is conditional: no `dispensing` record
  means `computeDepletion` (unedited, `lib/schedule/depletion.ts`) returns all-null, and B3 shows no
  meter and no estimate at all, never a fabricated one.
- **`durationDays`/`dosingPattern`/`doseTimes` on B4's still-unsaved draft** — `outcome.prescription`
  is a `Partial<Prescription>`, so every field B3 treats as guaranteed-present on a *saved* record is
  genuinely optional on B4's *draft*. `formatDurationDays`/`formatDoseTimes`/`patternLabel`
  (`features/prescription/format.ts`) all return `null` for an absent value on either screen, so the
  same `DetailRow` empty-mark behaviour holds on both without a second code path.
- **`Settings` row absent (بدر has none)** — not exercised by this bundle directly (بدر has no
  prescriptions to open), but `getSettings`'s own documented default (`adherenceCheckInEnabled:
  false`) is what B3's tracking-off note would key off if he ever gained one; nothing in this
  bundle's code assumes a `Settings` row exists.

## §7. Things this work found out the hard way

1. **The `confident` mock outcome sets `needsReview: false` but supplies no `startDate`.**
   `lib/data/index.ts`'s `submitPrescriptionImage` (unedited) returns `{ drug: { genericName:
   'Ibuprofen', brandName: 'Brufen', strengthMg: 400 }, dosePerAdministration: 1, frequencyPerDay:
   3, durationDays: 7, dosingPattern: 'daily', doseTimes: [...], needsReview: false, status: 'active'
   }` for the confident branch — no `startDate` anywhere in it. `savePrescriptionDraft` persists
   this as-is. CR-002's own invariant (1) reads "an `active` prescription with `needsReview: false`
   carries all five [fields]," which this saved record does not, strictly. `scripts/guards/
   seed-invariants.ts` never notices because it calls `reset()` and checks the **seed's own** static
   store, not a runtime draft an e2e run adds — so this never trips a guard — but it is a real gap
   between the mock's own confident-outcome shape and CR-002's invariant, worth the owner's or WP1's
   attention rather than silently working around it in this bundle's UI (out of `lib/**`).
2. **The mock's `(unreadable)` literal reads like a real drug name.** Both the seed's own `rx-006`
   (`drug.genericName: '(unreadable)'`) and the B4 mock's `needs_review` outcome use the identical
   literal string for "we could not read the drug name" — and `DetailRow` (correctly) renders
   whatever it is given, so both B3 (rx-006) and B4's needs-review review step show `(unreadable)`
   as if it were the medicine's name, rather than an empty mark. This bundle renders it verbatim,
   matching `features/caregiving/CaregiverPrescriptionDetail.tsx`'s (bundle h) own treatment of the
   same seed record, rather than inventing a hidden special case for one specific literal — flagged
   here as a real UX rough edge for the owner's bilingual copy pass, not fixed by branching on a
   magic string in this bundle's own code.
3. **`getFieldConfirmationQueue`'s `uncertainFields` derivation (`lib/data/index.ts`, unedited) never
   includes `'brandName'`** — its filter explicitly excludes it (`!(k === 'brandName')`). This is a
   different function from `submitPrescriptionImage`'s own `uncertainFields` (which *can* name
   `brandName`, though the mock's needs-review branch happens not to), so B4's "mark the uncertain
   field" behaviour and G3s's field-confirmation queue (bundle i, out of scope here) are not
   necessarily reading the same rule for what counts as uncertain. Noted for whichever bundle builds
   G3s, not acted on here.
4. **A drift found against F3 (bundle h's read-only twin, `features/caregiving/
   CaregiverPrescriptionDetail.tsx`), read at DEPENDENCIES §1 for parity** — see the REPORT BACK
   section below; not fixed in `features/caregiving/**` (out of this bundle's file list), only
   matched or deliberately diverged from in B3's own composition and reported to the lead.
