## What changed

1. **CR-090 (ii), the DDInter pending-exclusion bug (commit `30a9124`).**
   `agents/knowledge/src/screening.js` `exclusionReason` no longer excludes a
   prescription whose `fieldReviewStatus` is `'pending'` while `needsReview` is
   `false` (the CR-054 confident-save shape - nobody ever reviews that state, so
   excluding it left it silently unscreened forever). `'returned'` still excludes,
   as do `needsReview !== false` and an inactive status. `travel-check.js` shares
   the function and gains the same fix; `travel-check.test.js` is unchanged and
   stays green. Added a table test of `exclusionReason` and a pt-01 regression: an
   Ibuprofen prescription saved in the CR-054 pending shape is now screened and
   raises the Warfarin x Ibuprofen danger alert (DDInter900 x DDInter1951) instead
   of being dropped.

2. **`agent-extraction` reads the backend's own screening outcome (commit
   `a9f9f86`).** Since AP-10, `POST /api/agent/prescriptions` already screens (or
   holds) the prescription before it answers 201, and returns the outcome
   (`screening: 'screened'|'held'|'skipped'`). `agent-extraction` no longer calls
   `jurah/screen-prescription` itself: `EX_AFTER_SAVE` reads `w.body.screening`
   and computes `notScreened` (save committed, prescription unflagged, outcome
   neither `'screened'` nor `'held'`); the `'screen it?'` IF and the
   `'n8n: screen the new prescription'` HTTP node are deleted, `'after save'`
   wires straight to `'answer (deterministic)'`; `EX_ANSWER` sets
   `mustEscalate = saved.notScreened` and reports `screening: { outcome }`. The
   stale header/comment claiming a workflow file calls this webhook is fixed to
   name the backend's own `requestScreening` (`lib/agent-webhooks/core.ts`
   `screeningPayload`). `agents/knowledge/scripts/check.js`'s old drop-in check
   (which read the about-to-be-removed legacy workflow file) is replaced with
   literal assertions on the DDInter webhook's shape, and the extraction
   scenarios are rewritten for the new contract.

3. **The legacy screening is retired (D2/CR-074, commit `5eda2e3`).**
   `git rm agents/lib/screening.js agents/test/screening.test.js
   agents/workflows/agent-interaction-screening.json`. `agents/scripts/build.js`
   drops the `SCREENING` inline, the whole "3. agent-interaction-screening"
   section (`SC`, `SC_INPUT`, `SC_SCREEN`, the `screening` workflow object) and
   `screening` from the write list. `agents/scripts/check.js` drops the name from
   `NAMES` and deletes the legacy scenario block, including its
   `[TO BE SUPPLIED]` citation assertion. `tests/unit/agent/agents-contract.test.ts`
   drops the `agents/lib/screening.js -> parseAlertBody` describe (already
   covered by `knowledge-contract.test.ts`). `agents/test/drift.test.js` gained a
   test that `D.repoHashes()` no longer names `agent-interaction-screening` and
   does name `agent-interaction-screening-ddinter`, and that `D.compare` reports a
   live legacy workflow as "live, but no committed workflow file" rather than
   passing silently.

4. **The Telegram hand-off is removed, and an unscreened save fails loudly
   (commit `ea68386`).** A new static check, `oneScreeningCheck` in
   `agents/scripts/check.js`, reads every committed workflow under
   `agents/workflows/` and `agents/knowledge/workflows/` and asserts: exactly one
   webhook node anywhere sits on `jurah/screen-prescription` (the DDInter one); no
   other node anywhere even names that path; `agents/workflows` holds exactly the
   generated set plus `agent-error`. Run before `build.js` was touched, it was
   RED - see *Proof* below. Then `agents/scripts/build.js`: `EX_REPLY` drops
   `screen`/`screeningUrl`/`screeningBody`, reads `w.body.screening`, computes
   `notScreened` the same way as `agent-extraction`; the `'screen it?'` IF and the
   `'n8n: screen the new prescription'` HTTP node are replaced by
   `'saved but not screened?'` and a `Stop and Error` node ("saved but not
   screened - a human must look", naming the outcome), reached only after the
   patient's own Telegram reply is sent. This closes CR-098 item 1 in its
   post-AP-10 form: an unflagged save whose outcome is neither `'screened'` nor
   `'held'` now fails the n8n execution instead of saving silently with nobody
   alerted.

5. **Documents (this commit).** `agents/README.md` and `agents/knowledge/README.md`
   updated: the diagrams and the going-live steps drop every reference to the
   legacy screening and its credential binding; the "what is proven" / "honest
   limits" sections drop the legacy `[TO BE SUPPLIED]` reference-set sentence,
   fix the stale "not re-screened" limit (AP-10 already re-screens on
   confirmation), and add the CR-090 (iii) refill-duplicate limit;
   `agents/knowledge/README.md` gains a numbered "AP-04 cutover" section and an
   AP-18 `errorWorkflow` TODO. `docs/DECISIONS.md` gains `CR-100` at the end.
   Workflow and test counts in both READMEs are left as they are - that is
   AP-19's job, not this package's (per the plan).

## Live steps for the lead, in order (also written into `agents/knowledge/README.md`)

Retiring the legacy screening and turning on `JURAH_AGENT_SCREENING_URL` for the
first time are two different events; doing them out of order either
double-screens a Telegram save or leaves it unscreened.

1. Export the live workflows (recorded here once run).
2. **Unpublish the legacy `bMVDCQbSwUtMHJ4x`**, then at once import and publish
   `agent-interaction-screening-ddinter`, binding the inbound secret and the agent
   bearer. The old live `agent-telegram-inbound` keeps screening Telegram saves
   through it in the meantime - the DDInter workflow is a drop-in (same path,
   body and auth).
3. Set `JURAH_AGENT_SCREENING_URL` in Vercel and redeploy (AP-13).
4. Immediately republish the rebuilt `agent-telegram-inbound` and publish
   `agent-extraction`. Between steps 3 and 4 a Telegram save is screened twice,
   never zero times; doing step 4 before step 3 would leave saves unscreened and
   make them hit Stop and Error. Since AP-11 merged, the rebuilt
   `agent-telegram-inbound` also carries the Orchestrator, so AP-11's own live
   steps apply to the same publish: `agent-travel-check` must already be active on
   `jurah/travel-check`, and `Gemini: what is this photo?` and `n8n: travel check`
   get their bindings (`docs/backend-notes/ap-11.md`, "Live steps for the lead
   after merge").
5. Export again and show the diff.
6. Confirm the workflow list shows exactly one active workflow on
   `jurah/screen-prescription`.
7. **Run the drift check and get it to zero.**
