## 2. Where the mock cheated

*One row each: what the mock does now · what the backend must do instead · what breaks if it is missed.*

| Mock behaviour | Backend must | If missed |

| `REFERENCE_NOW` is a constant in `lib/config.ts`; the mock session, the schedule and every "is this past" decision read it (WP0) | decide before WP4 of Phase 2 whether the demo keeps a seeded clock offset or generates relative to the real clock (`Phase 2 — Backend Handoff.md` §6.2) | the seed's dose tables stop matching the screens on demo day |

*From `docs/backend-notes/wp4b.md` (wp4b, merged at its wave's gate):*

- **The Hawiati approval is a client-side timer, not a real identity provider.** `signIn(civilId)` (WP1's session module) already decides the whole outcome — steps 1–4 of `ROLES.md`'s resolution, including writing the session cookie for anything but `not_in_test_list` — the instant it is called. `features/identity/SignInForm.tsx` adds the "open the Hawiati app and approve" ritual entirely on top of that already-decided result: it shows the `Countdown` component running, waits a fixed ~2.1 real seconds (`APPROVAL_DELAY_MS` + `COMPLETED_DISPLAY_MS`, local constants in `SignInForm.tsx`, not `lib/config.ts` — they are a UI transition timing, not a value Phase 2 reads), then acts on the outcome it already had. **Phase 2 must reverse this order for real**: classify the Civil ID, then actually wait on Hawiati's callback/webhook before writing a session, and the visible countdown must be driven by whether that real approval has arrived — not by a fixed local delay. The "lapsed" state (`Countdown`'s own `onLapse`, fired at `HAWIATI_COUNTDOWN_SECONDS` = 25 real seconds) is real in the component and unit-tested (`tests/unit/identity/sign-in-form.test.tsx`, fake timers forcing a hang), but in this mock it can only be observed by making the mock itself hang — the real backend's 25-second window will be the actual Hawiati callback SLA, not a UI nicety.
- **"Remembers the last choice as the default" lives entirely in the session cookie, not in any per-account storage.** `ROLES.md`'s A1b line is satisfied by two mechanisms that are both WP1's, not this bundle's: (a) `signIn`'s `multiple_roles` outcome immediately writes a session for the **first** role option returned by `roleOptionsFor` (`lib/session/index.ts`'s own comment calls this a "mock shortcut"), so `getSession`/`getRoleOptions` are well-defined the instant A1b renders; (b) `chooseRole` (called by `features/identity/RoleChooser.tsx`) simply overwrites that session. Nothing persists a preference **across a sign-out** — the "last choice" is only remembered for the life of the current session/cookie, never keyed by Civil ID or Account. **Phase 2 must add a real per-account "last chosen role" field** (on `Account`, most naturally) that `signIn` reads to pick which option to default to on a fresh sign-in, not just "whichever option happened to come first in the array".
- **A2's optional caregiver-invite step is a placeholder Card, not a real invite flow.** The cross-bundle contract (this bundle's brief) named `InviteSheet` from `@/features/caregiving` (bundle h); that module did not exist yet when this step was reached during the build (see §7). `features/identity/SetupFlow.tsx` step 3 renders a quiet, clearly-labelled placeholder instead of inventing an invite implementation, and its "skip" control still advances the flow normally — nothing here creates, reads or writes a `Caregiver` row. This is a **build-sequencing** note, not a backend seam: once the lead wires the real `InviteSheet` in at this step, no data-layer function changes. **Superseded (lead, 2026-09-22 check):** the real `InviteSheet` is now mounted at `features/identity/SetupFlow.tsx:194`; A2's invite step calls `lookupMaskedName` and `inviteCaregiver` exactly as F1 does, and — as predicted — no data-layer function changed.
- **A3's push/chat status reads never trigger a real permission prompt or a real bot handshake** — `getPushState`/`getMessagingLink` (WP1's) already return the mock's stored rows; this screen only renders and links onward to E5, it calls nothing that simulates asking the browser or Telegram anything.

*From `docs/backend-notes/wp4h.md` (wp4h, merged at its wave's gate):*

- **The masked-name lookup is computed against an in-process directory, not a rate-limited service call.** `lookupMaskedName` (`lib/data/index.ts:458`, delegating to `maskedNameFor` in `lib/data/mock/accounts.ts:35` — not this bundle's files, read-only) resolves a Civil ID against the seed's `Account` rows synchronously, with no request throttling. **The backend must rate-limit this endpoint per session and audit every call** (`Acceptance Criteria and Test Plan.md`, Phase 2 §"Masked-name lookup") — it is the one endpoint that could be abused to enumerate Civil IDs, and Phase 1 has no rate limiter anywhere.
- **Invitation expiry is a string comparison against `REFERENCE_NOW`, not a clock.** `pendingInvitationsFor` (`lib/data/mock/caregivers.ts`) filters `expiresAt > nowIso` at read time; there is no scheduled job that flips a stale `pending` row to `expired` — the seed's `cg-05` is simply seeded already-`expired`. **The backend needs both**: expiry enforced at read time (so a stale row is never offered for acceptance even one request before a job runs) **and** a job that actually transitions the row, so F1's list and the audit log read a real status rather than a live recomputation forever.
- **The invite-sheet's Civil ID field has no format check beyond twelve digits client-side** (`features/caregiving/InviteSheet.tsx`'s `CIVIL_ID_PATTERN`). The real Hawiati/Civil ID format validation belongs server-side; Phase 1 never claims to validate it beyond shape.
- **`InviteSheet`'s "created" outcome has no per-invitation identifier of its own to poll or confirm against** — it is a static panel, not a submission receipt. Phase 2's real invitation-creation endpoint should still return an id (never displayed, G9) so the client can distinguish "created" from a transient network failure, which this mock cannot fail in a way worth simulating.

*From `docs/backend-notes/wp4d.md` (wp4d, merged at its wave's gate):*

`lib/data/index.ts`'s `submitPrescriptionImage` (unedited here — `lib/**` is out of this bundle's
file list) picks its outcome from the chosen image `Blob`'s **byte size** — 0 bytes → `unreadable`,
1–99 bytes → `needs_review`, 100+ bytes → `confident` — never a real vision/extraction call. This
bundle's `tests/e2e/prescription.spec.ts` and `tests/unit/prescription/AddPrescriptionFlow.test.tsx`
both reach every B4 state through this same byte-size switch, through the published API only
(`submitPrescriptionImage`/`savePrescriptionDraft`), exactly as the brief asks.

What Phase 2's real extraction pipeline must return, per outcome, for `AddPrescriptionFlow.tsx` to
keep working unmodified:

- **`confident`** — `{ kind: 'confident', draftId, prescription: Partial<Prescription> }` with every
  one of the five CR-002 fields present (`brandName` optional only for a genuine generic-only
  record) and `needsReview: false`. The mock's own confident branch is itself slightly short of this
  — its `Partial<Prescription>` has no `startDate` even though `needsReview` is `false` — see §7.1. **Superseded (CR-035, lead fix):** the confident branch now carries `startDate: REFERENCE_DATE` (`lib/data/index.ts:192`), so the mock meets the invariant; §7.1's matching remark is superseded the same way.
- **`needs_review`** — the same shape plus `uncertainFields: string[]`, naming exactly the contract
  field keys (`'strengthMg' | 'frequencyPerDay' | 'startDate' | 'doseTimes' | 'brandName' | ...`)
  the pipeline could not read with confidence. `AddPrescriptionFlow` marks only the fields named in
  this array with the "Unclear" empty mark — a field absent from the array but also absent from
  `prescription` still renders (correctly) with `DetailRow`'s own default "Not recorded" mark instead,
  which is the right behaviour for "the prescriber genuinely wrote nothing here" but the wrong one
  for "we could not read this specific field" if the real pipeline ever omits a field from both the
  object *and* `uncertainFields`. **The real pipeline must put every field it is not confident about
  into `uncertainFields`, even when it also has no value to offer for it** — otherwise the screen
  cannot tell "the prescriber left this blank" from "we could not read this."
- **`unreadable`** — `{ kind: 'unreadable' }` and nothing else. `AddPrescriptionFlow` never
  constructs a `Prescription` in this branch; the medicines list is provably unchanged

## 4. Fields a screen depends on

Derived from `docs/SCREENS.md`'s per-screen States/Components/Data-function columns against `types/contracts.ts`. Covers every `?` field in `types/contracts.ts`, plus the required fields whose absence would blank a screen. Three classifications:
- **Required, NOT NULL** — the field is already required in the contract, and a named screen renders nothing sensible (or the wrong thing) without it. Phase 2 must keep it NOT NULL.
- **Optional, screen-conditional** — the field is optional only while some other field holds a particular value (the CR-002 pattern); once that condition clears, a named screen needs it and Phase 2 must enforce the pair at write time.
- **Optional, genuinely** — no screen requires it under any condition; its absence is a normal, permanent state, not a gap to be filled later.

**Re-derived from the shipped code on 2026-09-22.** The first version of these tables was read off `docs/SCREENS.md`'s plan; the lead re-checked every row by grepping each field's readers under `features/`, `components/` and `app/` (comments excluded) and mapping the reading file to its screen. 26 rows named a screen that never reads the field, 19 omitted a real reader, and eight fields a screen renders unconditionally had no row at all. “Indirectly” below means the field is read only server-side, behind the seam (the generator, the depletion module, `lib/data/index.ts`), so the screen depends on a *derived* value, not on the field itself. Fields marked *(read by no screen)* are in the contract and in the seed, but no screen renders them — Phase 2 may keep them nullable without breaking any screen.

## 7. Things Phase 1 found out the hard way

*An honest list: what was awkward, what was asked, what a screen needed that the contract did not have.*

- Guard 4 (G1) is a static approximation: it forbids dose-status literals in object construction outside the seed and the generator, assignments to `.status` with a dose word, `actions` on notifications, and data-function names that suggest recording a dose. It cannot prove the absence of a write path the way a server refusal can — which is exactly why §3 exists. **Runtime proof beside it (owner, Gate 0b):** `tests/e2e/g1-today-tracking-off.spec.ts` signs in as حمد and asserts the B1 dose list contains zero `<button>`, zero `<input>`, zero `onClick` handlers, zero `role="button"` and zero status pills. It is red until B1 exists (WP4 bundle c); it is never skipped.
- `strengthMg` is a misnomer the contract keeps for compatibility: it holds the number in `strengthUnit`'s unit. Guard U (`scripts/guards/no-unit-conversion.ts`) forbids any arithmetic on it; Phase 2 must store and return it unconverted and never add a conversion in the API layer.
- `tokens.json` does not carry `--font-sans`, the eight type styles as CSS, or the structural constants (44px hit area, 3px ring, 880px cap) the brand book states in prose; `scripts/build-tokens.ts` emits them so `bundle.css`'s port has every variable it reads.
- **Sheet's positioned ancestor (WP3).** `Sheet.md` positions against the nearest positioned ancestor, so every shell wrapper (`AppShell` — which `ClinicNav` composes rather than duplicating it — and the no-shell signin/invitation layouts) sets `position: relative` on its outermost element; no bundle adding a `Sheet` later needs its own positioning context.
- **`TabBar` refuses a single-item set (WP3, CR-030).** Its tuple type is 2/3/4 items, but a single-clinic-role account has exactly one destination; `ClinicNav` renders no bar at all in that case rather than a filtered or disabled one. Owner to bless the absence or add a `[T]` member.
- **Navigational tabs and rows are real `<a href>`s (WP3).** `onChange`/`onClick` is reserved for genuine actions with no URL (role switch, sign-out); active state derives from the pathname server-side, so no client sync exists to break.
- **This Next version's special files (WP3, vendored docs, not memory).** `not-found.tsx`/`error.tsx`/`global-error.tsx` receive no `params`; `not-found` recovers its locale from the `x-jurah-path`/`x-jurah-locale` headers `proxy.ts` stamps, and `error.tsx` (a Client Component) from `usePathname()`. The reset callback is named `retry`, not `reset` — a breaking rename the vendored docs flag.
- **`useSearchParams` must sit under `<Suspense>` (lead, Gate 3, D-008).** `next build` fails prerendering any statically renderable route whose client tree calls it bare (`missing-suspense-with-csr-bailout`; the signin pages hit it). `LanguageSwitch` wraps its query-aware link with a pathname-only fallback; the rule stands for every future bundle.
- **CR-020's phone-width sign-out is provisional (WP3, D-007).** No clinic screen owns a shared AppBar yet, so the quiet sign-out sits beside the simulated-role banner at phone width until bundle i builds the real clinic screens; the shared `SignOutButton` moves without rework.
